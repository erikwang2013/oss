## 切片 2：大对象流式（债务主攻）

**预研结论（钉子）**：写路径已把 body 磁盘暂存（`harvest_body` → `tmp/part.1`），内存峰值只在
「读回 part.1 → 整份 `ec::encode` → 12 片」一步（≈2.25× 对象）；MPU complete 峰值 ≈2.5×。
EC 按**列**独立（`ShardByShard` 逐列编码），任意按「data 的整数倍」切块流式编/解都成立。

**设计决定**：
- 块宽 `W = 64 KiB`（每片每块输出 W 字节）；输入块 = `data×W = 512 KiB` → 输出 12×64 KiB。
  末块输入补零到 `data×W`（全片定长 `shard_size = 块数×W`，格式不变——`shard_size` 本就在 meta 自描述）。
  **语义兼容而非逐字节兼容**：旧读端按 meta 的 `shard_size` 重建，新旧数据互读成立；对拍测试改按「旧写新读 + 新写旧读」。
- 远端分片：`ShardWrite` 加 `offset: u64`（0=建/截断）与 `chunk_crc32c`（**逐块**校验，保住「服务端先验后落」）；
  整片 CRC32C 由写端增量累计（`crc32c_append`）存 meta。`ShardRead` 加 `offset/length`（0,0=整片，向后兼容）。
- 读路径：整读 → 逐块解码攒进输出（峰值 2×→1×+O(块)）；**Range 只读命中块**（seek = 块号×W；本地 seek+read、
  远端 offset/length）。缺失块用 EC 重建后做**逐块对偶校验**（同一块号切片降维成 12×W 的 rs.verify）——
  Range 读不依赖整片 CRC（现格式没存逐块 CRC，不宜为它膨胀 meta）。
- 内联（≤128 KiB）与 `ec.enabled=false`（part.1 原样）路径不动。`max_put_bytes` 保留为防护上限（不再是必要约束）。
- 本轮**不做**整读的 HTTP 层流式（`get_object` 返回 `Bytes` 的 API 形态不动；改流式是后续独立项，收益只有峰值 2×→1×）。

- [ ] `ec.rs`：逐块编/解辅助（定宽块、增量 CRC、末块补齐、逐块 verify）——**预研修正：不需要
      `ShardByShard`**，普通 `ReedSolomon::encode/reconstruct/verify` 按列独立，逐块喂 `12×W` 切片即可
- [ ] `put.rs`：`stage_payload`/`stage_payload_multi` 换分块编（12 个本地句柄追加写 / 远端逐块 `write_shard(offset, chunk_crc)`）
- [ ] `read.rs`：`read_ec` 逐块（整读），`get_object_range` 走命中块（连 parity 块一起读+重建+verify）
- [ ] `mesh.rs` + `xl-proto` + `xl-client`：两个 RPC 的字段扩展与服务端切片读写
- [ ] MPU complete 流式（part 文件顺序逐块喂编码器）；`mpu.rs:455` 注释收口
- [ ] 测试：分块边界（W 倍数 ±1、跨块 Range、末块补零截断）往返 cmp；**新旧互读对拍**（旧写→新读、新写→旧读，用 git stash 对照或保留旧编码器函数直接对拍读路径）；内存峰值实测（96 MiB 对象 /usr/bin/time -v 峰值 < 50 MiB）；既有 EC 单测全绿
- [ ] 收口注释：`put.rs:129`、`ec.rs:3`、`read.rs:87/142`、`store.rs:1178`

## 执行模型

- 主会话 = 唯一写者（crates/web/docs 全归它，串行切片）；**团队 = 验证与记账**：`verifier`（每切片四闸 + 对抗核查）、
  `e2e-runner`（关键节点跑真进程 e2e）、`docs-fixer`（README/定稿段落，只碰 docs）。
- 每切片收口顺序：单测绿 → clippy/fmt 绿 → verifier 对抗核查 → 定稿 → 本地提交（不推送）。
- 内存纪律：同一时刻只跑一个重活（编译/e2e/镜像构建），背景见宿主 OOM 史（e2e 全文 18m34s 单次跑穿前有三次被杀记录）。
