# M6 数据流 实施计划（工作令）

> 设计文档 §7.2（事件总线）/ §7.1（作业引擎）/ §M6 阶段表；功能规格 §10（复制）/ §11（通知）/ §12（Select）。
> **验收**（设计文档 §M6）：
> ① Kafka 消费者收到 `ObjectCreated` 事件，字段与 S3 通知格式一致
> ② 关掉 Kafka 期间产生的上传，Kafka 恢复后全部补投，不丢不重
> ③ `aws s3api select-object-content` 对 CSV 与 JSON 各返回正确记录流；`--request-progress` 事件帧格式正确
> ④ 桶复制：源桶写入后远端出现同 ETag 对象，`x-amz-replication-status` 从 PENDING → COMPLETED
> ⑤ 远端不可达期间积压进 `repl_outbox`，恢复后自动追平
> ⑥ Select 的 SQL 子集边界测试：不支持的语法返回明确的 `InvalidRequest`，而非错误结果

## 钉子（防蔓延）

- **不做**：webhook / AMQP / SNS 目标（`Notifier` trait 抽象，本片只落 Kafka 实现——不建独立 contrib
  crate，记档设计偏差）；`ObjectAccessed` 事件默认**关闭**；Parquet（后置）；交互式查询；GZIP 解压后
  随机寻址（顺序解压）；跨站点复制（M7/M9）；`ExistingObjectReplication` 做**参数校验**但不回溯存量
  （AWS 语义 = 仅对新写入生效才默认；显式 Enabled 的存量回溯记档延后）；复制带宽限速（记档）。
- **依赖**：`rskafka`（纯 Rust Kafka 生产者）· `sqlparser`（AST，AWS 方言求值器自写）；`csv`/`flate2`
  已在依赖缓存；**出站 S3 客户端不引 reqwest 栈**——用 `s3s-sigv4`（已在依赖树，`derive_signing_key`
  /`calculate_signature` 均 pub）手拼 hyper 客户端（Replication 用）。
- **事件总线分层**（保持 crate 依赖方向）：xl-s3 定义 `EventSink` trait（发射点注入，OssS3 持
  `Option<Arc<dyn EventSink>>`）；oss-server 实现（写 `event_outbox` + worker 投递）。xl-s3 不依赖
  oss-server。
- **事件投递语义**：outbox 持久化 + 每事件每目标一次成功投递；失败指数退避重试，超限进死信
  （`state='dead'`，控制台可见）。**至少一次**（崩溃在「已发未删」窗口可能重复——行业惯例，README
  写明；e2e 以 seq 集合断言「不丢 + 无重复（稳态）」）。worker 经 guarded UPDATE claim（多实例安全，
  同 M4 job 模式）。
- **复制的远端定义**：`remotes` 走 **oss.toml 静态配置**（`[[remotes]] id/endpoint/ak/sk/region`，
  配置文件信任同集群 `secret`；设计文档的 remotes 表 + 控制面 CRUD 归后续——**偏差记档**）；规则
  走 S3 API（Put/Get/DeleteBucketReplication），`Destination` 引用 remote id + bucket。
- **复制状态**存 `xl.meta`：`Version.replication_status: Option<String>`（白名单
  `PENDING|COMPLETED|FAILED|REPLICA`，decode 校验；**golden 第八次**有意识更新）。HEAD/GET 回
  `x-amz-replication-status`；写入即 `PENDING`，worker 成功置 `COMPLETED`、重试超限置 `FAILED`。
  **REPLICA 防循环**：复制客户端投递时带 `x-amz-replication-status: REPLICA` 头；接收端记录为
  REPLICA；worker 跳过 REPLICA 版本（客户端可伪造该头=自选不复制——记档信任边界）。
- 发布/推送：仍只在用户明确口令时执行。

**计划评审 v2 修订（2026-10-17，verifier-m6-plan 五阻断全闭合；报告 plan-review.md）**：
- **R1 重试语义分级**（B1）：错误分两类——**连接类**（网络不可达/超时/连接层 5xx）**不吃死信预算**：
  保持 pending、退避封顶 5min、last_error 记录，**永不 dead**（验收 ②/⑤「全部补投/自动追平」的语义
  载体）；**永久类**（4xx 鉴权/协议/topic 不存在/事件损坏）计 attempts，超 10 次 → dead/FAILED
  （需人工处置，控制台可见）。
- **R2 outbox 租约**（B2）：claim = `UPDATE … SET claimed_at, next_retry_at=now+60s WHERE id IN
  (SELECT … state='pending' AND next_retry_at<=now LIMIT n)`；worker 每轮回收
  `claimed_at < now−lease` 的挂起行（崩溃自愈）；补 claim→崩溃→回收 的测试。
- **R3 切片重排 + 状态入口**（B3）：原切片 3/4 成环 → 拆为「3 复制状态面（先）→ 4 桶复制（后）」。
  状态写入**不**扩散 store 写 API 形参（评审枚举 47 调用点）：改为**独立入口**
  `store.set_replication_status(bucket, key, version_id, status)`（meta 重写 + epoch 抬升，同
  legal-hold setter 先例；仅规则命中/REPLICA 摄入路径调用，非复制用户零开销）；`ObjectInfo` 增
  `replication_status: Option<String>` 出参供 HEAD/GET 头。切片 3 含 meta 字段（golden 8）+ 入口 +
  出参 + 头 + REPLICA 摄入（服务读头传 set）。
- **R4 验收③ 帧格式载体**（B4）：帧的线上格式（prelude/headers/CRC32）是 **s3s 的序列化责任**
  （`into_byte_stream` 已核）；我方责任 = **事件序列与节奏**——单测钉：Records 分片内容、Progress
  每 ~1MiB 触发、Stats 三计数恒等式、End 收尾、异常中途 Error 帧；e2e 用 `aws s3api
  select-object-content --request-progress` 实跑（CLI 自带帧解析，能正常结束即线上帧合式）+ 记录
  断言。README 记档此口径切分。
- **R5 发射点补全 + 事件口径**（B5）：补三条写路径——aether ingest（`s3:ObjectCreated:Post`）、
  console 删对象（`s3:ObjectRemoved:Delete`）、lifecycle worker（`s3:LifecycleExpiration:{Delete,
  DeleteMarkerCreated}`）；**事件类型三档矩阵**：对象事件（Put/Post/Copy/CompleteMultipartUpload/
  Delete/DeleteMarkerCreated，写路径直发）· 生命周期事件（lifecycle worker 发）· **ObjectAccessed
  本片不实现**（配置校验拒绝 + 记档——spec 默认关，开关留后续）· `Replication:*`（M7 才发，记档）·
  LifecycleTransition（M8，记档）。校验白名单 = 前两档（配置其它 → 400）。

**v3 修订（2026-10-17，v2 增量复评附项全收；报告 plan-review.md「## v2 增量复评」）**：
- **V1 R1 可执行判据**（按评审表原样）：
  - Kafka（rskafka 0.6 `client::error::Error`）：**可重试/永不 dead** = `Connection`/`Timeout`/
    `RetryFailed`/`Request(IO|Poisoned|Read/Write 帧错)` + `ServerError` 的
    `UnknownServerError|UnknownTopicOrPartition|LeaderNotAvailable|NotLeaderOrFollower|
    RequestTimedOut|BrokerNotAvailable|ReplicaNotAvailable|StaleControllerEpoch|NetworkException|
    Coordinator*|NotEnoughReplicas(AfterAppend)|NotController|KafkaStorageError|FencedLeaderEpoch|
    UnknownLeaderEpoch|ThrottlingQuotaExceeded|OffsetNotAvailable|PreferredLeaderNotAvailable|
    EligibleLeadersNotAvailable|UnstableOffsetCommit|UnknownTopicId|Unknown(i16)`；
    **永久（>10 dead）** = `SaslAuthenticationFailed|TopicAuthorizationFailed|
    ClusterAuthorizationFailed|UnsupportedSaslMechanism|IllegalSaslState|SecurityDisabled|
    InvalidTopicException|MessageTooLarge|RecordListTooLarge|UnsupportedCompressionType|
    UnsupportedVersion|InvalidRequiredAcks|InvalidRecord|InvalidRequest|PolicyViolation|
    CorruptMessage|RequestError::NoVersionMatch`；**未归类默认可重试**（护验收②⑤）；
    **topic 缺失归可重试**（`UnknownTopicOrPartition` 有 spurious 语义；produce 用
    `UnknownTopicHandling::Error` 让 outbox 观察，不用 `Retry`）；
  - hyper 复制：**可重试** = `hyper::Error` 的 connect/timeout/incomplete/canceled/closed/IO（URI 构造
    错误归永久）+ HTTP **408/429/全部 5xx（不区分代理/应用层）** + 未知默认；**永久** = 400/401/403/
    404/405/409/412/413/422/501、301/307/308、TLS 证书校验失败。`404 NoSuchBucket` → 目标桶预创建
    为部署前置（README 写明）。
  - attempts 语义：每次投递失败递增用于退避；**dead 仅 `class==Permanent && attempts>10`**；
    连接类永不 dead；**租约回收不计 attempt**；`classify_event_err/classify_repl_err` 表驱动单测。
- **V2 R2 租约模型 = 两态单钟**（评审方案 A）：`state ∈ {pending, sending, dead}` + `claimed_at`；
  claim = 原子 `UPDATE … SET state='sending', claimed_at=now WHERE id IN (SELECT id … WHERE
  state='pending' AND next_retry_at<=now ORDER BY seq LIMIT n)`（`RETURNING`/`BEGIN IMMEDIATE`）；成功
  DELETE；失败 `state='pending', claimed_at=NULL, next_retry_at=now+backoff`；**回收仅
  `state='sending' AND claimed_at<now−lease`**（置回 pending，`next_retry_at=now`，不计 attempts）。
  完成/失败 UPDATE 带 claim token（`WHERE id=? AND claimed_at=? AND state='sending'`，
  `rows_affected=1` 才生效——防 stale sender 复活）。**lease：事件 60s（rskafka produce 超时 30s），
  复制 300s**（大对象整读+流式 PUT 可超 60s；不给心跳续租，超 300s 的复制目标由 e2e 上限约束，记档）。
  `event_outbox` 补 `claimed_at` 列（v2 表漏列勘误）。投递顺序：claim `ORDER BY seq`、**逐条串行**
  投递（跨 target 不承诺序；验收②只要求不丢不重，e2e seq 集合断言）。
- **V3 R3 三补**：①marker 状态口径——`set_replication_status` **允许 marker 版本**（marker 无数据但
  状态在 meta 合法；仅拒「版本不存在」），与 legal-hold 的 marker 拒绝不同并有测试钉；②**复制入队点
  统一在服务端后写派发**（与 R5 同一 sink 入口）：S3 面六路径 + aether/console/lifecycle 三路径经
  同一 dispatcher 派生 event_outbox + repl_outbox——**复制覆盖全部写入口**（超 spec 最小面，记档）；
  ③顺序/崩溃窗：enqueue 先于 `set(PENDING)`；PUT 响应前 await set（HEAD-after-PUT 必见 PENDING）；
  commit 后 set 前崩溃 → 无 status 但已入队，worker 终置 COMPLETED（记档）。
  ④头实现勘误：s3s 的 `HeadObjectOutput`/`GetObjectOutput` 已有 `replication_status:
  Option<ReplicationStatus>` 字段（序列化器自动加 `x-amz-replication-status`）——**用 DTO 字段**，
  不用 with_headers。
- **V4 R4 口径细化（2026-10-18 订正）**：Stats 三计数定义——`BytesScanned` = 输入原始字节（压缩则
  压缩后）、`BytesProcessed` = 送入求值器字节（压缩则解压后）、`BytesReturned` = Records payload 字节；
  三计数**相互独立、无排序恒等式**（投影可令 returned > processed；空 GZIP 可 processed < scanned），
  测试只按定义逐项断言。CLI 不输出 Progress/Stats payload、只证明帧可解析——README 记档该切分。
- **V5 R5 source 入口**：emit 签名携 `EventSource { host, port, user_agent }`——S3 面自请求
  `Host`/`User-Agent` 头解析（缺省回退 listen 配置，host 语义 = 端点而非客户端，AWS 同）；内部路径
  （aether/console/lifecycle）占位 `host="internal", port=0, user_agent="oss-{aether|console|
  lifecycle}"`。不引 ConnectInfo。
