# oss (TunTun) — A Self-Built Distributed Object Storage System

[简体中文](README.md) | English

![License](https://img.shields.io/badge/license-Apache--2.0-blue.svg) ![Rust](https://img.shields.io/badge/rust-2024%20edition-dea584.svg) ![Release](https://img.shields.io/github/v/release/erikwang2013/oss) ![S3](https://img.shields.io/badge/S3-compatible-blueviolet.svg)

**Chinese project name: 吞吞 (TunTun) · English name: oss · Project pet: TunTun (吞吞)** — a little creature that swallows object blocks into its bucket.

An S3-compatible, self-built distributed object storage system (an equivalent implementation of MinIO). It supports multi-drive erasure coding 8+4, inter-node gRPC mesh, versioning, lifecycle, bucket policies and auditing, three SSE modes and object lock, STS temporary credentials, event notifications/Kafka, S3 Select, bucket and multi-site replication, access points/Object Lambda, Batch/Inventory/tiering, sync buckets and a 3-voter Raft control plane. The default `aws-cli`/`rclone` large-file paths (automatic multipart for ≥8 MiB) and resume habits work directly; the browser console supports chunked uploads and management.

**Latest release: v1.19.0 (2026-10-26).** This is the Wave1 foundations release: DP-1 mixed-version data-plane gating, Raft feature levels 1..3 with OSSCTL3, tenancy schema/backfill, M8 run-state snapshots, `maintenance` containment mode, and the read-only `cluster-shrink plan`. All are verifiable foundations/previews: shrink apply, Raft tenancy account APIs, the M8 multi-node runtime, and production Level C Ext commands are not delivered; boundaries are documented below.

- **Five crates with one-way dependencies `oss-server → xl-s3 / xl-client → xl-store` (`xl-client → xl-proto`)**: `xl-store` is the storage kernel with no framework dependencies (the commit protocol and `xl.meta` format are persisted per the final design); `xl-s3` implements s3s's S3 trait on top of the kernel; `xl-proto` holds inter-node gRPC protocol messages and services (generated by prost + tonic-build); `xl-client` is the tonic implementation of the mesh (`TonicMesh` client + server-side handler); `oss-server` assembles an axum Router with e-cat, serving the console API, aetherupload chunked uploads, and the S3 service at the same time.
- **Two client entry points**: `aws-cli` / `rclone` go through the S3 surface (SigV4 authentication); the browser console (React 19 + antd, M1b) goes through `/api/v1` and aetherupload's bundled scripts (chunking / resume after disconnect / instant upload).
- **Tech stack**: Rust 2024 · ecat 7.0 · s3s 0.17 · aetherupload-rust 3.0.0 · axum 0.8 · sqlx / SQLite · serde + rmp-serde.

Disk layout quick note (M2b multi-drive): each drive holds one **complete namespace** — under `<drive>/<bucket>/<flattened-key>/` are `xl.meta` (this drive's replica) and version directories `<uuid>/part.1.<shard>` (the shards that land on this drive; in single-drive form, all shards). **A commit is always "data in place first → meta flip"**: single drive = rename on the same drive; multi-drive = two-phase meta commit per drive (prepare `xl.meta.new` on all drives ≥ quorum before flipping each to final; reads pick the **newest replica**). Small objects (< 128 KiB) are inlined into `xl.meta` and do not get data files. With encryption enabled (M5), data files hold **ciphertext shards** (encrypt then EC), and the wrapped DEK and `key_id` are recorded inside `xl.meta` (the metadata itself contains no plaintext keys). Scratch areas are under `.oss.sys/{tmp, trash, locks}` on each drive; the `drive-id` drive identity marker prevents using the wrong drive.
Control-plane metadata (users/keys/buckets/upload records/instant-upload index) lives in SQLite.

## Request Lifecycle

![Request lifecycle](docs/assets/request-flow.svg)

Both entry points (direct S3 upload, browser chunked upload) converge at xl-store's **commit protocol**: stage → rename data into place on the same drive → overwrite `xl.meta` to commit; everything before commit is invisible to clients. EC writes/reads (including range reads) are chunk-streamed: peak memory ≈ the block buffer (MiB level), independent of object size (a 96 MiB object measured VmHWM 107 MiB).

## Object Lifecycle

![Object lifecycle](docs/assets/object-lifecycle.svg)

The read path trusts only `xl.meta`: directories without valid meta are never served; a crash can only leave invisible debris (orphan version directories / leftover trash / incomplete multipart staging areas). At startup the service self-checks and clears `tmp`/`trash`; `oss-server clean <days>` reclaims the remaining debris by mtime.

## Getting Started

```bash
# 1. Start the service (on first start it automatically creates data directories, staging directories, bucket directories, and the admin)
OSS_ADMIN_USER=erik OSS_ADMIN_PASSWORD=changeme cargo run -p oss-server

# 2. Log in to get a token (M1 still has no registration UI; the account comes from the env vars above)
TOKEN=$(curl -s -X POST localhost:9000/api/v1/login -H 'content-type: application/json' \
  -d '{"username":"erik","password":"changeme"}' | python3 -c 'import json,sys;print(json.load(sys.stdin)["token"])')

# 3. Create a pair of access keys for S3 clients (specified explicitly, matching the AK/SK in the acceptance section below; running it again reports "access key already exists" and is idempotent)
curl -s -X POST localhost:9000/api/v1/access-keys -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -d '{"access_key":"AKIA_TEST_ACCESS_KEY","secret_key":"SK_TEST_SECRET_KEY_0001"}'
```

> Note: the staging drive's `_header/` and the per-group directories are both created at startup by `aether::build_runtime` (group directories via `aetherupload::console::list_groups`, with `_header/` created separately — list_groups only creates it as a side effect when creating its own root directory); if preprocessing reports a generic upload error, first check whether the staging drive directories were cleaned up.

> Known limitations:
> - The four `/aetherupload/*` routes **require JWT**: after login, access with the cookie `oss_token` or `Authorization: Bearer <token>` (the frontend sets the cookie on successful login, M1b); missing/bad/expired is always 401. A full role/policy model still follows the deployment shape (M4+).
> - ListObjects v1 is supported (marker / NextMarker / delimiter / max-keys); rclone can still use `LIST_VERSION=2`.
> - A single PUT / single part is still subject to `max_put_bytes` (default 256 MiB); a multipart large object as a whole is not constrained by that value.
> - Multipart: `UploadPartCopy`, `ListMultipartUploads` (including cluster `ListUploadsLocal`), GET/HEAD `partNumber` are supported; `partNumber` together with `Range` → 400 `InvalidRequest`.
> - `partNumber` depends on `part_sizes` persisted at Complete time; **objects ingested via replication/tiering do not carry this field**, so their `partNumber` degrades to the old semantics (only part 1 = whole object; >1 → 416). To address by part, use an original MPU upload.
> - Range: HEAD supports a single range (200 + ranged `Content-Length`/`Content-Range`, out of range 416); GET multi-range (`bytes=0-9,20-29`) does not return `multipart/byteranges` — s3s strips Range before parsing → 200 whole object. If a client includes Range in SigV4 SignedHeaders, after stripping it gets 403 `SignatureDoesNotMatch`; presigned URLs are unaffected.
> - Object tags: `Put/Get/DeleteObjectTagging`, PUT's `x-amz-tagging`, GET/HEAD's `x-amz-tagging-count` are supported; ≤10 tags, key ≤128 / value ≤256 Unicode scalars, invalid → 400 `InvalidTag`. Tags are stored per version; replication ingestion (`REPLICA`) does not persist tags. MPU tags are supported; the console can edit object tags.
> - CopyObject directives: `x-amz-metadata-directive` / `x-amz-tagging-directive` (COPY/REPLACE, two independent axes) are supported; REPLACE not provided means clear; same bucket same key only metadata REPLACE unlocks; a tagging header carried during COPY is ignored.
> - **Console pages**: M5 encryption/KMS read-only status, M6 event page and Select workbench, M4 bucket policy editing and audit query, object tag editing, bucket default encryption, notification dead-letter replay are supported; see the "Console Pages (S6)" section.
> - Multipart **part-level** `x-amz-checksum-*` is not validated (silently ignored; the combined semantics are still unimplemented, recorded); single-part PUT's Content-MD5 / `x-amz-checksum-*` are validated before the commit point (mismatch → `BadDigest`, object not persisted).
> - The console's "upload records" are registration history: after an object or staging file is deleted, the record row remains (by design, as an audit trail).
> - `oss.toml`'s default `listen = "0.0.0.0:9000"` and placeholder `jwt_secret` are for local development only; before external deployment you must switch to loopback binding and a random secret (the placeholder secret can be used to forge console and `/aetherupload/*` tokens; combined with 0.0.0.0 binding it is a LAN risk surface).
> - **Multi-drive (M2b) operational boundaries**:
>   - Configuring `data_dirs` with 2..11 drives **errors out** at startup (the redundancy of EC 8+4 requires ≥ 12; a single drive can run but has no redundancy, with a startup warn). `[ec] enabled=false` restores the old M1 form (single drive only).
>   - **Before first start, confirm each drive's mount point is mounted**: at first start, an "unmounted mount point directory" is indistinguishable from a brand-new drive and will be initialized as a new drive. A drive that goes offline at runtime is automatically judged out-of-registry (writes bypass per quorum, object deletion fail-closed, automatic recovery when reinserted), but it **must have started once while mounted** (the drive has `.oss.sys` and `drive-id`).
>   - With an offline drive present, **deleting objects/buckets returns 500** (to prevent "reinsert and resurrect"); this is intentional fail-closed; retry after reinsertion.
>   - Meta replica newest-selection has ranked by `(epoch, mod_time)` since M4 — the write side increments epoch monotonically +1, so NTP rollback no longer produces "old replica wins by big clock"; epoch is forward-compatible with `xl.meta` (old files participate in ranking as 0).
>   - The directory-fsync zero-loss-on-power-failure guarantee assumes ext4/XFS; on other filesystems directory fsync failure only warns, and you must verify yourself.
> - The long-run acceptance (rclone concurrency 100×100 MB + interrupt retry, design acceptance #3) is in the `E2E_LONG=1` gated section of `tests/e2e_s3.sh` (skipped by default, triggered manually; `E2E_LONG_N`/`E2E_LONG_MB` adjust scale).
> - **Permissions system boundaries**:
>   - Authorization model = per (sub-account × bucket) three tiers (read/write/delete) + bucket owner full rights + admin full rights; **no row = no permission**. The three entry points — S3 surface (AK/SK), console, and aetherupload upload — enforce the same decision.
>   - Sub-accounts can create **their own buckets** in the console / S3 (automatic full rights); bucket deletion is limited to the bucket owner or admin; legacy buckets (no ownership record) are visible only to admins.
>   - Admins can **disable/enable** accounts (Users page): disabling invalidates the whole chain (login 401, existing JWT 401 on the next request, AK 403, upload surface 401; there is no active revocation list, it relies on validation on the next request). Anyone can **self-service change password** on the "Access Keys" page (verifying the old password); admins can also reset passwords for others.
>   - Console uploads can only go to "the target bucket mapped by `[[groups]]`" — sub-accounts that want to upload to their own buckets use the S3 surface.
>   - Revoking authorization does not retroactively affect **in-flight chunked uploads** (those already admitted by preprocess will finish); new requests take effect immediately.
>   - The create-sub-account API always creates non-admin accounts (prevents privilege escalation); passwords are at least 8 characters; deleting a user cascades cleanup of their keys and grants.
>   - Passwords are stored as **Argon2id** (m=19456, t=2, p=1); legacy sha256 passwords are **transparently upgraded on successful login** (no reset needed).
>   - **Login rate limiting (C1)**: account dimension, ≥5 failures in a 10-minute window → locked for 10 minutes; global dimension, ≥120 failures in a 60-second window (across usernames, preventing random-username floods from hammering Argon2) → temporary rejection for everyone (429 + `Retry-After`). Single-process in-memory state: each node independent, reset on restart (rate limiting is not a persistent quota). Only the login entry is protected; authenticated password changes are not covered.
>   - **Bucket policies only take effect on the S3 surface**: the console and aetherupload upload surface still use the three-tier permissions.
>   - **Deleting a bucket also clears that bucket's policy and lifecycle rules** (both S3-surface and control-plane bucket deletion do this) — recreating with the same name does not inherit them, preventing old rules from mistakenly deleting.
> - **Multi-set (M4) boundaries**:
>   - Under multi-set, **the data plane adds +1 local DB query per op** (bucket → set; only on a local miss does it fan out to peers; single-set adds zero). Resolution is fail-closed: transport errors / set out of range / inconsistent peer answers are all propagated upward, **never silently falling back to set0**.
>   - **Cross-set bucket-name uniqueness is best-effort under concurrent bucket creation** (the same as the existing cross-node duplicate-check TOCTOU).
>   - **The target bucket of `[[groups]]` groups is pinned to set0** (the console upload surface does not participate in new sets).
>   - **Adding drives is only allowed in the last set** (forward-rolling constraint): adding drives to a middle set → startup fingerprint refuses to start, infeasible.
> - **Encryption and object lock (M5) boundaries**: see the recorded sections in "Encryption (M5)" and "Object Lock (M5)"; cross-node key points — the bucket lock state columns (`buckets.object_lock*`) propagate with the control-plane row broadcast and are **eventually consistent**: during the window, non-versioned overwrite/reclamation paths **fail-closed and refuse deletion** (no silent pass); row synchronization strong consistency is deferred to M9. **Multi-node encryption requires distributing the same master key (file or full KMS directory) to all nodes** before writing, otherwise this node cannot read objects written by other nodes.

## Docker (compose)

**Single-host** (oss-server + console nginx):

```bash
docker compose up --build        # console http://localhost:8080 · S3/API http://localhost:9000
```

**M3 cluster** (4 nodes × 3 drives = 12 slots; service names are node addresses):

```bash
docker compose -f docker-compose.cluster.yml up --build
# S3/control-plane entry: n1:9000 · n2:9001 · n3:9002 · n4:9003 (any node equivalent); console :8080 reverse-proxies n1
```

- Config: single-host `docker/oss.toml`; cluster `docker/cluster/n{1..4}/oss.toml` (static topology, comments in the files).
- **Secrets auto-generated**: if `jwt_secret` / cluster `secret` / admin password are **not filled in**, they are auto-generated at first start (64 hex) and persisted on the host to `./docker/secrets/generated.env` — mode 0644, just `cat` it to see the admin password, already gitignored; the four cluster nodes share the same copy (flock serializes, concurrent first starts converge to the same copy). **Rotate = delete the file and restart**; to use your own values: fill them explicitly in `oss.toml` / `OSS_ADMIN_PASSWORD` (explicit values win, never overwritten).
- Data/staging in named volumes (only cleared by `docker compose down -v`); the cluster uses independent volumes per node.
- S3 clients **connect directly to node ports** (SigV4/streaming do not go through nginx); the console goes through the :8080 reverse proxy.
- Images: `Dockerfile` (oss-server release build, includes protoc) and `docker/Dockerfile.web` (vite build + nginx).
- In the cluster compose, node `addr` uses service names (hostnames) — bootstrap resolution binding + peers dial by name (one config serves both).

## Console (M1b)

```bash
# 1. Start the backend (same as M1a)
OSS_ADMIN_USER=erik OSS_ADMIN_PASSWORD=changeme cargo run -p oss-server
# 2. Start the frontend (open another terminal)
cd web && npm install && npm run dev
# 3. Open http://127.0.0.1:5173 and log in with the account above
```

- Uploads reuse aetherupload's bundled scripts (chunking / resume after disconnect / instant upload); the frontend contains no chunking logic
- **Sub-accounts** (admin menu): create/delete sub-accounts, check read/write/delete grants bucket by bucket; after a sub-account logs in it sees only authorized buckets (the menu has no "Sub-accounts" page), and upload/delete buttons are shown/hidden by permission (backend 403 as the backstop)
- **Cluster** (admin menu): mode / slots / quorum-unmet count + node table + topology fingerprint (15s auto-refresh); single-host shows a single-host mode hint
- **Upload destination**: uploads land in buckets by upload group (`oss.toml`'s `[[groups]]`, e.g. `file` → `files`); the object name = the whole-content MD5 + extension, subdirectory = UTC year-month (e.g. `202610/<md5>.bin`). So in the object browser you find files by content hash, not by original filename
- The instant-upload hint "Upload successful (instant upload)" means 0 chunks were transferred
- e2e: `cd web && npx playwright install chromium && npm run e2e`. Playwright bundles dual webServer (`cargo run` + `vite`); the backend auto-starts as `pw` per `web/playwright.config.ts`; **an already-running backend will be reused** (`reuseExistingServer`), and in that case the running instance's admin password must also be `pw`, otherwise login is 401 — if the password doesn't match, first stop the self-started service and let Playwright start its own with `pw` (`changeme` in the "Getting Started" section is only a placeholder example).
- The 1 GB upload and resume-after-disconnect are **manual verification items** (not in e2e): `head -c 1073741824 /dev/urandom > /tmp/1g.bin` → upload via the panel and watch the progress advance → mid-way DevTools → Network → Offline (or unplug the network cable) → the output area shows "Network failure, retrying…" → restore the network → it automatically continues to success; after download `cmp` matches the local file.
- Resume-after-disconnect is limited to the same page session; after a refresh you must re-upload (cross-refresh resume is unscheduled; currently limited to the same page session)

## Ops Commands

`oss-server [serve|groups|build|clean <days>|fsck [--repair]|heal|scrub|rebalance [--dry-run|--apply]|cluster-shrink plan --to <target.toml> [--json]]` (no arguments = `serve`). Ops commands read `oss.toml` from the current directory and go through the same startup bootstrap as the server (create directories/connect DB/open storage; admin and bucket bootstrap are idempotent):

```bash
oss-server groups        # create group directories (idempotent; startup bootstrap also does it; run it first to confirm when uploads report a generic error)
oss-server build         # rebuild the instant-upload index from current drive state (clear the old index first, then full-scan the staging drives)
oss-server clean <days>  # reclaim debris older than <days> by mtime:
                         #   staging drive `_header/` and `*.part`; data drive `.oss.sys/{tmp,trash}` orphans
                         #   and unreferenced version directories under each object directory (incl. incomplete upload staging areas)
oss-server fsck          # full-drive inspection: orphan version directories / EC shard missing-or-bad (CRC32C) / tmp-trash counts /
                         #   stray shard files (rebalance/crash leftovers; --repair deletes them);
oss-server fsck --repair #   same as above + minimal repair (delete orphans + read-time shard repair). Report written to
                         #   `.oss.sys/fsck/<timestamp>-<kind>.json`
oss-server heal          # fsck --repair full run + missing bucket directory recreation (cluster difference set) + per-version repair
                         #   (historical versions are also read by explicitly naming the version to trigger write-back); run on each node — local semantics:
                         #   fixes gaps on the local drives; cluster convergence = run once on each node
                         #   same prohibition as fsck --repair: must not run concurrently with in-flight uploads/writes (read-time repair/orphan
                         #   cleanup competes with in-flight version directories)
oss-server scrub         # full deep inspection (read-only): read every block of every EC version + per-block 12×W dual verification
                         #   (locates bad shards; constant memory, does not assemble the whole object); full historical version coverage;
                         #   healthy objects count as ok_versions; repairable bad/missing blocks do not exit non-zero (data is still within
                         #   EC redundancy, the read path self-heals); only deep failures (insufficient live shards / dual verification failure) exit 1 (cron can watch)
oss-server rebalance     # scale-out migration (dry-run by default): migrate existing objects to flattened placement (placement=v2;
                         #   no-op if not enabled); per-object copy→flip under lock→clear old shards, idempotent and re-runnable;
                         #   report `<timestamp>-rebalance[-dry].json` (operation order see the "Scaling" section)
oss-server cluster-shrink plan --to <target.toml> [--json]
                         # read-only shrink validation (all nodes in maintenance): per-set slot count/parity/
                         #   capacity/epoch+hash/MPU on retired nodes must all pass before a plan is written to
                         #   `.oss.sys/shrink/<old>-<new>-plan.json`.
                         #   apply/verify/commit/rollback are not delivered (see "Shrink Planning")
```

Division of labor: `fsck` = whole-shard CRC32C quick check (light); `scrub` = block-level deep verification (slow, can locate bad shards).

Suggested cron (daily `clean 1` and `build` once each, weekly `fsck --repair` once):

```cron
17 4 * * * cd /path/to/oss && ./oss-server clean 1
47 4 * * * cd /path/to/oss && ./oss-server build
23 4 * * 0 cd /path/to/oss && ./oss-server fsck --repair
```

- `clean` decides by mtime: an upload whose duration is still within the reclamation window will not be mistakenly deleted; a long-hanging upload beyond the window (reachable only via direct S3 upload; aether and local uploads are minutes-scale) may be judged expired while still in progress — this write fails, no data loss; `days` is limited to 1..=36525
- `build` clears the instant-upload index first and rebuilds per drive: concurrent uploads at the rebuild instant fall back from "instant-upload hit" to a normal upload, no data loss
- Unknown subcommand or invalid arguments print usage and exit 2; command failure exits 1
- The config file path is fixed to `oss.toml` in the current directory (the former `oss-server <config-path>` usage has been removed)

## TLS (Transport Encryption)

Plaintext by default (behavior identical to older versions when there is no `[tls]`). After configuring `[tls.server]`, the main HTTP/S3/console listener, witness, Raft RPC, inter-node gRPC mesh, site/repl/tier outbound, and Kafka all enable TLS — a single switch, no "half TLS" mode. Certificates are read and validated at startup; the main listener, outbound reqwest/rustls, Raft, **mesh gRPC clients** and **Kafka TLS clients** hot-reload on SIGHUP/interval after a successful material swap (in-flight work keeps the old client). The mesh gRPC **server listener** still takes a startup snapshot, and Kafka SASL remains startup-scoped, so inbound mesh changes need a rolling restart.

```toml
[tls.server]
cert = "/etc/oss/server.crt"
key  = "/etc/oss/server.key"
# Optional: require and validate client certificates (mTLS). S3/console/Raft clients on the shared listener must all present one.
client_ca = "/etc/oss/ca.crt"

[tls.client]
# Extra outbound trust roots (platform roots always participate in validation); configure for self-signed/private-CA deployments.
ca_cert = "/etc/oss/ca.crt"
# Optional: outbound client identity (mTLS; client_cert/client_key must be paired).
client_cert = "/etc/oss/client.crt"
client_key  = "/etc/oss/client.key"
```

- Peer addresses can still be written as `http://` (cluster nodes, site endpoint, Raft `advertise_endpoint`, stretch): connections are upgraded to https per `[tls.server]`. When `[tls.server]` is not enabled, writing `https://` is rejected at startup (no silent downgrade to plaintext). `[listen]` is recommended to contain only `host:port`.
- `[[remotes]]`/`[[tiers]]` `endpoint` supports `http://`/`https://`; when the certificate hostname doesn't match the endpoint, override with `server_name` (https only).
- Kafka: `[[kafka.targets]].tls = true` enables SSL; `sasl` supports PLAIN / SCRAM-SHA-256 / SCRAM-SHA-512, and must be combined with `tls = true`. SNI is fixed to the broker hostname; the certificate SAN must match.
- mTLS is opt-in on the shared listener: once enabled, **all** clients (S3, console, Raft, site) must present a CA-issued client certificate; there is no `verify=false` bypass.
- Outbound (site/repl/tier/Kafka/mesh) always validates the platform roots + `[tls.client].ca_cert`; mTLS identity uses `[tls.client].client_cert/client_key`.

## Cluster Mode (M3)

**Static topology**: flat node × drive, configuration is topology (no DC/region hierarchy). No `[cluster]` = single-host (local behavior byte-for-byte identical to v1.4.0); configuration requires **slot count ≥ data+parity (12)**.

```toml
[cluster]
node_id = "n1"
secret  = "cluster-internal-token-change-me"   # shared token for inter-node gRPC (plaintext, private-network assumption)

[[cluster.nodes]]
id = "n1"
addr = "127.0.0.1:19101"   # this node's gRPC listener (HTTP port configured separately)
drive_count = 3
# …n2/n3/n4 are identical in shape
```

Startup: each node places its `oss.toml` in its own directory (`data_dirs` three entries = drive_count 3) and runs `oss-server serve`; order doesn't matter (rolling-startup liveness probes only warn; a reachable peer whose node_id doesn't match the config refuses to start, preventing miswiring).

**Explicit slot topology (v1.19.0, shrink prerequisite)**: `[cluster]` optionally takes `epoch` and `[[cluster.slots]]` (`{set?, node, drive}`; slot number = file order within the set, `set` defaults to 0). `epoch = 0` means the positional topology; once declared, slots must be contiguous from 0, match the `[[cluster.nodes]]` node order/drive_count, and must not be mixed with positional entries. Explicit slots participate in the topology hash; nodes advertise `topo_epoch`/`topo_hash` via NodeHealth for mixed-version gating and shrink validation.

**Maintenance mode (v1.19.0 preview)**: top-level `maintenance = true` returns 503 XML `ServiceUnavailable` + `Retry-After: 60` for every non-GET/HEAD/OPTIONS HTTP request, and pauses background workers and recovery; it is mutually exclusive with `[raft]` (it would block Raft RPC, so config validation refuses to start). Use it only for shrink/maintenance windows.

**Critical numbers (4 nodes × 3 drives = 12 slots, EC 8+4)**:
- Stop 1 node (9 slots left = exactly Q_s): **write has zero margin** (all 9 shards must succeed, client retries converge), read 9≥8 has margin; this configuration **is at the critical point with a single node failure** — for margin use 6×2 (12 slots, stop 1 leaves 1 spare).
- Stop 2 nodes (6 slots <9): writes rejected (lock/meta quorum unmet → 5xx); **reads are equally unreachable** — GET returns `500 CorruptMeta` (**not 404**; "insufficient quorum coverage" must not be disguised as "does not exist").

**Configuration counter-example**: 4×4 = 16 slots **do not use** — EC has only 12 shards, `shard % 16` only lands on slots 0..11, the 4th node has zero shards, and stopping any shard-holding node leaves 8<9, making it even more likely to be unwritable.

**Operational guidance**:
- Each node periodically runs `clean` + `fsck --repair` (same cron as above); **remote orphans are only reclaimed by that node itself** — while it is offline, other nodes cannot delete its debris. Missing shards are covered by read-time repair + fsck inspection; missing-key meta is detected from peer difference sets by `fsck --repair` and recreated ("fill in after re-adding the node"; for batch use `heal` — difference-set fill-in + bucket directory recreation + per-version repair).
- While a node is offline, `clean`'s object-directory reclamation **conservatively no-ops** (all-node liveness check before irreversible data deletion); `trash/tmp` as usual.
- **`fsck --repair` must not run concurrently with in-flight multipart uploads** (age-less orphan deletion will clear staging areas).
- **M3 does not support in-place upgrade from single-host to multi-node** (M4's rebalance only covers scaling an existing cluster): to move single-host data into a cluster, re-ingest it.
- `data_dirs` order is part of the topology: misordering is rejected at startup by the `.oss.sys/topo` fingerprint (loud failure).

**Observability**: `GET /metrics` (Prometheus text; **public**, with comments noting it exposes the same magnitude of information as `/health/cluster`) — `oss_quorum_unmet_total{op="write"|"lock"}` · `oss_node_up{node=…}` · `oss_drive_count` · `oss_slot_count`. M9 additionally exposes `oss_raft_role{role="leader"|"follower"|"witness"}`, `oss_raft_term`, `oss_raft_last_applied`, `oss_raft_members`, `oss_raft_production_ready`, `oss_raft_leader_changes_total`, `oss_raft_apply_errors_total`, `oss_raft_forward_total`, `oss_raft_snapshot_bytes`; the sync surface `oss_sync_acked_total`, `oss_sync_failed_total`, `oss_sync_write_intent_recovered_total`, `oss_sync_delete_partial_total`, `oss_sync_delete_recovered_total`, `oss_sync_ambiguous_total`; the stretch surface `oss_stretch_slots_ok` (0 when `[stretch]` is not configured). The console "Cluster" page (admin menu: mode / slots / quorum-unmet count + node table + topology fingerprint, 15s auto-refresh; single-host shows a single-host mode hint) and `GET /api/v1/cluster/status` (admin; graceful degradation to `mode:"single"` on single-host) share the same source.

**Node health (v1.19.0)**: mesh `NodeHealth` adds `data_wire_version`, `topo_epoch`, `topo_hash`, `drives` (per-drive set/drive/free_bytes) and `maintenance`; `GET /health/cluster` adds `data_wire_version`/`data_plane_compatible`/`degraded_peers`/`incompatible_peers`, and each node carries `data_wire_version` (null when unreachable), which shows mixed-version windows and degraded state.

**Known boundaries (M3)**:
- Multipart upload (MPU) sessions are **routable across nodes**: cluster Create returns `<base64url(node_id)>.<uuid>`; subsequent UploadPart/Complete/Abort/ListParts on any node are streamed to the owner over the mesh (1 MiB chunks, SSE-C key only inside the cluster). Owner unreachable/unknown → 503. Bare-UUID/legacy uploads remain local; mixed-version clusters do not forward (fail-closed), and rolling upgrades keep legacy uploads sticky. A lost Complete response then `NoSuchUpload` on retry is standard S3 behavior and does not double-commit.
- Inter-node locks have no write-side fencing: the lease TTL is much larger than a single write operation; the backstop is version-uuid isolation (interleaved writes leave at most orphan directories, reclaimed by each node's clean; committed data is not corrupted).
- The control plane (accounts/permissions) is **read-fan-out**: an AK minted on any node is usable cluster-wide; writes still land only on the local node (cross-node strong consistency is deferred to M9).
- Inter-node gRPC is plaintext by default; after configuring `[tls.server]`, mesh / Raft / site / repl / tier / Kafka all use TLS (see the TLS section). traceparent is lightly propagated (with `RUST_LOG=debug` you can sample the same trace id across both nodes' logs; full OTLP is deferred to M4).
- Naming: oss-server's aetherupload `staging_dir` ≠ the storage kernel's `.oss.sys/tmp`.
- **Upgrades (v1.19.0 / DP-1)**: the M9 Raft control plane supports Level B rolling upgrades (baseline v1.13.1; steps in item 6 of the "cutover / force recovery runbook"), followers/learners first, leader last, `feature_level` defaults to 1. The data plane now has **mixed-version gating**: nodes advertise `data_wire_version`/`topo_epoch`/`topo_hash` via NodeHealth, placement v2 writes only to wire-2 peers with the same epoch/hash, and incompatible peers fail closed (never silently fall back to v1). During a mixed-version window: ListObjects V1 across a legacy peer returns `x-oss-degraded: list-marker` (boundary keys may repeat, the marker advances); ListObjectVersions fails closed on legacy peers; ListMultipartUploads may omit entries in its union and returns `x-oss-degraded: mpu-union`; the MPU forwarding gate rejects legacy owners. **Still not promised**: real-binary rolling e2e for the data plane or TLS material hot rotation; production upgrades still need a maintenance window.
- **EC range-read semantics** (M4 slice 2): Range reads no longer do whole-shard CRC32C / object-level SHA256 (instead per-block 12×W dual verification, bad shards are locatable and self-healing); **corruption outside the range no longer triggers read-time repair** (full reads still do), batch repair goes to `heal` (M4 slice 4).

## Scaling (rebalance, M4)

Append-only scaling: placement switch (`placement = "v2"`) + tail-append topology + per-object migration. **Operation order** (the order cannot be changed):

1. **Upgrade the binary on all nodes** (placement still defaults to v1, behavior unchanged).
2. Add `placement = "v2"` to each node's `oss.toml` — **synchronized across all nodes**. During the mixed-version window **some writes degrade/fail** (diagnosable): shard requests sent/forwarded by old nodes have no slot (proto unknown field → 0), and the new server validates "slot 0 owner" and rejects (except the slot-0 owner itself); the reverse (new→old) old server ignores unknown fields and recomputes per v1 = correct results under v1. **During the upgrade window do upgrades only, do not carry business writes; enable `placement="v2"` only after all nodes are upgraded.**
3. Append topology (add drives/nodes, see below).
4. Run `oss-server rebalance --dry-run` on each node to review the plan.
5. `oss-server rebalance --apply` (idempotent, re-runnable to continue migration; same-drive migration uses the **hardlink fast path**, C4 — avoids whole-shard recopy, crash-safe, automatically falls back to chunked copy across devices).

**Adding drives**: only append `data_dirs` to the **last node** (adding drives to a middle node shifts the slots of subsequent nodes and is refused at startup by fingerprint). A new drive must first be "registered" — on the already-mounted new drive run
`mkdir -p <drive>/.oss.sys && cp <any-old-drive>/.oss.sys/drive-id <drive>/.oss.sys/`
(the existing policy against shadow-mount-point impostors does not allow automatic initialization of non-first-start drives).
Note: **the number of drives per single node must not exceed parity** (default 8+4 means ≤4 drives per node; exceeding it refuses to start) — adding a drive is 3→4, not 3→5; for more capacity add **nodes** (new nodes are likewise ≤4 drives).

**Adding nodes**: append to the tail of `cluster.nodes` + start the node with its own config. **After adding nodes you must also set placement=v2 on all nodes + rebalance** (v1 identity placement never uses new slots).

**Single-host multi-drive**: above 12 drives, v2 is automatic (no config needed); old objects are migrated with `rebalance`.

**Boundaries**: shrinking (removing nodes/drives) has **read-only planning only** (v1.19.0: `maintenance=true` + explicit-slot target topology + `cluster-shrink plan`; apply/verify/commit/rollback and the 4→3 e2e are not delivered); **config rollback is also infeasible** (old slot references fail-closed 500), only forward-rolling works; only one rebalance at a time; `rebalance` and `fsck`/`heal` **must not run concurrently** — fsck's stray scan would delete half-finished new shards "copied but not flipped" during migration as debris (object-level self-healing can re-run, but a migration round is wasted); migration residual windows and old-shard cleanup are covered by `fsck` (stray shard scan, run after rebalance stops).

## Shrink Planning (v1.19.0 preview)

Read-only planning; it moves no data and changes no topology:

```bash
# Target config: maintenance = true; [cluster].epoch = old epoch + 1;
# [[cluster.slots]] explicitly lists the retained slots (each set has fewer slots than now).
oss-server cluster-shrink plan --to shrink.toml --json
```

`plan` validates fail-closed: all nodes `maintenance=true`, reachable, and on the same `topo_epoch`/`topo_hash`; the target slot map keeps the same set count/slot counts, node order and drive_count, with at most parity retained slots per node; retired nodes have no in-flight MPU; free capacity ≥ bytes to copy; `.oss.sys/shrink/active.lock` is exclusive. On success it writes `.oss.sys/shrink/<old>-<new>-plan.json` (per-set slot counts, moves, retired nodes, object/version counts, capacity and warnings). Warnings do not block: minimum set slots − max slots per node < data+1 (no write margin after losing a node), or target free space < 2× the copied bytes.

**Not delivered**: `apply`/`verify`/`commit`/`rollback`, `.oss.sys/topo` v4, and a real 4→3 e2e; shrink must not be treated as executable today.

## Versioning (M4)

`aws s3api put-bucket-versioning --versioning-configuration Status=Enabled` to enable; `list-object-versions` to enumerate; GET / HEAD / DeleteObject with `--version-id` for a named version; `copy-object --copy-source 'bucket/key?versionId=<old>'` is **rollback** (old version → new version); DELETE without a version id = delete marker (GET 404, hidden from object listings, visible in version listings). Section 16 of `tests/e2e_s3.sh` covers this with live tests.

**v1 boundaries (honest record)**:
- Versioning has three states: `Off` / `Enabled` / `Suspended`. Off→Enabled, Off/Enabled→Suspended are allowed; changing back to `Off` is still rejected (`NotImplemented`, preventing whole-chain replacement from losing history); Object Lock buckets and M9 sync buckets reject Suspended (`InvalidBucketState`). Under Suspended, PUT/Complete only replace the null version, DELETE without a version id appends a null delete marker, and `versionId=null` can delete it by name; `get-bucket-versioning` on a bucket that never had versioning returns `Off` (AWS leaves it empty).
- All write responses expose `x-amz-version-id` (PUT / Complete / Copy / DeleteObject; DeleteObject also carries `x-amz-delete-marker: true`); GET / HEAD also return the actual version id. Point-named GET / HEAD of a marker version → 405.
- Object listing (ListObjectsV2) only sees keys whose "chain tail is not a marker"; range reads on historical versions follow the same S3 semantics.
- `ListObjectVersions` v1 **ignores delimiter** (produces no CommonPrefixes); when the continuation point (key-marker / version-id-marker) doesn't match the chain it returns 400 InvalidArgument (fail-loud).
- Cluster: version append still goes through write_meta quorum (whole meta rewrite); `list-object-versions` cluster path is per-key quorum reads (low-frequency operational surface; add paged RPC when scale demands — recorded).
- Object lock (M5): a lock-enabled bucket must have versioning Enabled (the create-bucket flag enables it automatically too); deletion semantics for locked versions are in the "Object Lock (M5)" section.

## Lifecycle (M4)

Configure via the console API `PUT /api/v1/buckets/{bucket}/lifecycle` (body is an array of rules, **full replacement**; bucket owner or admin), read back via `GET` on the same path; the S3 `Put/Get/DeleteBucketLifecycleConfiguration` and the console share the same validation. Rule structure (old flat fields remain compatible, new fields take precedence and are mutually exclusive):

```json
{"rule_id":"cold","enabled":true,
 "filter":{"prefix":"","tags":[{"key":"env","value":"prod"}],
           "object_size_greater_than":1024,"object_size_less_than":1048576},
 "expiration_days":30,
 "expiration_date":"2026-12-31",
 "expired_object_delete_marker":false,
 "transitions":[{"days":7,"storage_class":"GLACIER","tier":"t1"}],
 "noncurrent_version_expiration":{"noncurrent_days":30,"newer_noncurrent_versions":2},
 "noncurrent_version_transitions":[{"noncurrent_days":30,"newer_noncurrent_versions":2,
                                    "storage_class":"GLACIER","tier":"t1"}]}
```

Filter prefix/tag/size/And and Expiration.Date/ExpiredObjectDeleteMarker, Transition.Date, multiple transitions, noncurrent expiration/transition are all supported; `AbortIncompleteMultipartUpload` is still 501 (needs an MPU index). The background worker scans per `OSS_LIFECYCLE_INTERVAL_SECS` (default 60s; explicit `0` disables the worker), with the expiry decision `now - last_modified ≥ expire_days×24h` (**0 = expire immediately**). Versioned buckets write a **delete marker** by default (no physical deletion); noncurrent rules are computed by "new version creation time"; non-versioned buckets = whole-key delete.

Progress: `GET /api/v1/jobs` (admin) shows recent jobs (scanned / deleted / skipped / state / error, one per rule).

**Boundaries**:
- Transition/tiering is deferred to M8.
- **Run only one serve instance at a time**: each instance attaches its own worker (multiple instances execute repeatedly; idempotent but wasted work).
- **Large-bucket performance**: the worker lists the whole prefix of that bucket once per cycle — for very large prefixes, increase `OSS_LIFECYCLE_INTERVAL_SECS`.
- **Starvation boundary**: a single round of a single rule is ≤100,000 keys (100 pages × 1000); beyond that it **stops and records jobs.error** (`state=error`, not silent) — but the **scan position is not persisted across rounds**, so if a prefix has long-term >100,000 "not yet expired" keys, trailing expired keys may never be scanned (split the rule with a smaller prefix to fix).
- **Stale job rows**: a process crash may leave jobs rows with `state='running'` (no automatic reclamation; the display layer can identify them by an old updated_at).

## Bucket Policies and Auditing (M4)

Console API `GET/PUT /api/v1/buckets/{bucket}/policy` (bucket owner or admin; **bucket does not exist = 404** — prevents pre-setting a policy for a bucket that doesn't exist yet and having a same-named bucket inherit it later): `PUT` is **full replacement** (≤64 KiB, ≤100 statements, top level must be an object, `Effect` must be `Allow`/`Deny` with Principal/Action/Resource non-empty; exceeding the supported subset or a typo is 400, not silently no-op), `GET` reads back the original text (unset = `null`). S3-surface decision: **explicit Deny wins → Allow elevate → no match falls back to the three-tier permissions**; policy read/parse failure fail-closed denies. `CopyObject` **decides the source/target axes independently**: the target bucket write policy and the source bucket read policy are judged separately, **source bucket Deny overrides target bucket Allow** (otherwise someone with target bucket write permission could bypass source bucket Deny and copy out secrets), and **source bucket Allow cannot substitute for target bucket write permission**. `DeleteObjects` **authorizes per key**: batch-deleted keys are in the request body and invisible at the `check` stage, so authorization is delegated to the handler for per-key decisions (same criteria as single-key delete — policy Deny → reject / Allow → permit / no match → fall back to three tiers); denied keys are recorded in the response `errors[]` as `AccessDenied` and audited, the rest are deleted as usual (§3.4 partial-failure semantics; otherwise a prefix-level Deny would be bypassed by a single batch delete request).

Supported subset (`crates/xl-s3/src/policy.rs`): `Effect` · `Principal.AWS` (`"*"` | AK | `"uid:<n>"`) · `Action` (exact or trailing `*` wildcard, e.g. `s3:Get*`) · `Resource` (bucket-level `arn:aws:s3:::<bucket>` / object-level `arn:aws:s3:::<bucket>/<prefix>*`, **matched on a single axis by op category** — bucket-level ops see only bucket ARNs, object ops see only object ARNs, consistent with AWS). **Explicitly not done**: Conditions / NotAction / NotResource / Principal ARN forms (`Condition` is only supported in AP policies with `IpAddress`/`NotIpAddress` + `aws:SourceIp`, see the "Access Points" section). Explicit Deny also applies to bucket owners and admins (AWS semantics, proven by e2e) — admins only bypass the three-tier permissions, not bucket policy Deny.

**Anonymous (credential-less) access**: `Principal:"*"` still means "any valid AK" for signed requests; for credential-less requests it participates in decisions only on the **data-plane whitelist** `GetObject` / `HeadObject` / `PutObject` / `DeleteObject` / `DeleteObjects`, and must be explicitly Allowed by the bucket policy. No policy / no match / policy read failure are all 403 (fail-closed); explicit Deny wins. Listing, bucket create/delete, policy/ACL/versioning/lifecycle/encryption/object lock/tag/retention/legal-hold, MPU, CopyObject, console API, etc. are 403 even if the policy says `s3:*`. `DeleteObjects` at request level only requires "a bucket policy exists", then re-evaluates per key (denied keys go into `errors[]`, the rest are deleted). Anonymous requests are audited as uid=0 with detail `anonymous:*` / `policy:*`; the decision happens before object lookup, so a rejection does not leak whether the key exists. Anonymous requests carrying object-lock/retention/bypass headers are always 403 (see "Object Lock").

Auditing: every authorization decision on the S3 surface (both allow and deny) writes a SQLite `audit_log` row, with `detail` recording the policy source (`policy:allow` / `policy:deny` / `policy:error`); **retention cleanup (C5)**: after `OSS_AUDIT_RETENTION_DAYS` (default 0 = no cleanup) is enabled, rows whose `ts` is beyond the retention period are purged hourly (best-effort, failures only warn).
(`policy:allow` / `policy:deny` / `policy:error`); `GET /api/v1/audit?limit=&decision=allow|deny` (admin only; limit defaults to 100, clamped 1..=1000; `decision` only accepts allow/deny, other values mean no filtering, newest first).
Section 17 of `tests/e2e_s3.sh` covers it live (Deny wins / validation 400 / audit query / clear policy restores / delete bucket clears policy / per-key authorization for batch delete).
**Anonymous rejection rate limiting (M1)**: anonymous **allow** decisions are always fully logged; anonymous **deny** decisions are rate-limited by a process-level token bucket (burst 20, refill 5/s), dropped during floods (warn once per cumulative 1000), preventing unauthenticated traffic from unboundedly bloating `audit_log`. Anonymous requests carrying object-lock/governance-bypass headers are always 403 (see "Object Lock").

## Multi-set (M4)

The horizontal-scaling form of multiple EC groups (sets) in one deployment: new sets add capacity, **old sets zero re-layout**; single-set (k=1) is byte-for-byte identical to existing deployments (RPC default fields, fingerprints, placement all equivalent; in-place upgrade = append `set=1` entries at the end, old segments untouched).

**Configuration**: `[[cluster.nodes]]` gains an optional `set` (default 0). The same physical node can emit one entry in multiple sets (same `id`, **`addr` must be identical** — inter-node RPC routes only by id; inconsistency refuses to start); set numbers must be contiguous from 0 (missing numbers fail-closed). **`data_dirs` ordering contract (hard)**: concatenated in ascending set order, within a set in node declaration order; the sum of this node's `drive_count` across sets == `data_dirs.len()` (self-checked at open). Each set independently goes through the full topology validation (slots ≤255, ≥ data+parity, drives per node ≤ parity in multi-node; the flat union is additionally constrained by total drives per node ≤255).

```toml
[[cluster.nodes]]          # set0 segment (default, may omit set): one entry each for n1..n3
id = "n1"
addr = "127.0.0.1:19101"
drive_count = 3
# n2 / n3 identical…

[[cluster.nodes]]          # set1 segment: another entry for the same physical node (in-place upgrade = append at the end, old segment stays in front untouched)
id = "n1"
addr = "127.0.0.1:19101"   # addr must be identical for the same id across sets
drive_count = 3
set = 1
# n2 / n3 identical…
```

**Bucket pinning to a set**: console bucket creation (`POST /api/v1/buckets`) accepts an optional `set` (validated < number of sets; **default automatic assignment** to the set with the fewest buckets, C3); S3-surface CreateBucket (the protocol has no set parameter) likewise **automatically assigns** to the least-loaded set (single-set is always 0). Ownership is stored in the `buckets.set_id` column (old DBs get the column idempotently at startup, existing rows = 0). **A set is immutable once created** — there is no API to change a set, and existing buckets do not migrate across sets.

**Isolation semantics**: a set only constrains **data shards** (placement formula and shard RPC write/read/delete); **bucket directories and `xl.meta` are mirrored across all sets** (namespace surface: one complete namespace replica per drive, iterating all drives) — empty bucket directories and metadata replicas appearing on drives of non-owning sets is expected, not cross-group leakage.

**Topology fingerprint**: one per drive. Set0 segment drives write `v2 node=… slot=…` (byte-for-byte identical to single-set deployments, no rewrite), set>0 segment drives write `v3 set=… node=… slot=…` (slot is the **in-group slot**); `v3` with `set=0` = refuse to start (the write path never produces that form).

**Scaling constraints**: adding drives is only allowed in the **last set** (adding to a middle set shifts subsequent segments → startup fingerprint refuses); existing buckets do not migrate across sets — multi-set adds capacity for new buckets, not redistribution of existing data.

**Observability**: `GET /api/v1/cluster/status` (admin) adds a `sets` array (one entry per set: in-group slot count, node table, whether this node belongs to that set); the top-level `nodes` / `slot_count` are the id-deduplicated union of nodes (namespace-surface semantics). **Each set's slot numbers are an independent slot domain and will collide across sets — read grouped by set** (the console "Cluster" page already groups by set, C2).

## Encryption (M5)

**The order is a hard constraint: encrypt first, then erasure-code** — the write path is `plaintext → block-aligned streaming encryption (AES-256-GCM, DARE-style 65520B plaintext units → 65536B ciphertext units) → EC encoding → persist`, and the read path is the reverse; therefore **a single shard (below quorum) contains no plaintext information at all**, and parity blocks likewise (acceptance ②).

Three modes are selected by request header (**with no env configured = encryption disabled entirely, zero behavior change**):

| Mode | Enable / request | Key source | What is stored on disk |
|---|---|---|---|
| SSE-S3 | env `OSS_MASTER_KEY_FILE=<path>`; header `x-amz-server-side-encryption: AES256` | single master-key file (default `<data_root>/.oss.sys/master.key`, auto-generated at first start with 0600; **multi-node must distribute the same one**) | wrapped DEK, `key_id="file"` |
| SSE-KMS | env `OSS_KMS_DIR=<dir>`; header `aws:kms` | multi-key directory `key-<n>.bin` (current key = largest n) | wrapped DEK + `key_id="k<n>"` |
| SSE-KMS explicit CMK | as above plus header `x-amz-server-side-encryption-aws-kms-key-id: <name\|arn>` (must accompany `aws:kms`) | named CMK ring `OSS_KMS_DIR/cmk/<name>/key-<n>.bin` (name `[a-z0-9-]{1,64}`, created via admin API) | wrapped DEK + `key_id="cmk:<name>:k<n>"` + `kms_key_id=<canonical CMK name>` |
| SSE-C | headers `x-amz-server-side-encryption-customer-{algorithm,key,key-MD5}` (32B client key sent with every request) | client | **only `base64(MD5(key))` verification value stored (AWS's same 24-char header), the key never touches disk** |

- Each object gets a 32B DEK (generated by OsRng); unit nonce = random seed (8B) ‖ BE32(unit number); the unit number bijects (EC shard, block) to ciphertext units — nonces are not reused under the same DEK.
- Response headers: PUT / HEAD / GET return `x-amz-server-side-encryption` (SSE-C additionally returns customer-key-MD5 and other verification headers); `aws-cli`'s `sse` parameters work directly.
- **Semantics**: ETag / Content-MD5 / SHA256 are all computed over **plaintext** (protocol semantics unchanged); shard CRC32C over **ciphertext**; SSE-KMS explicit CMK (`…-aws-kms-key-id`) accepts a bare name or `arn:…:key/<name>`, and the CMK must exist in this node's key ring (missing/invalid → 400 `InvalidArgument`, fail-closed, never falls back to the default key); mutually exclusive with SSE-C; reading/deleting SSE-C objects must carry the same key (wrong key → 400, the verification value is the criterion). An ARN is only an addressing form: records and object responses echo the **canonical CMK name**, while GetBucketEncryption echoes the id exactly as configured (name or ARN).
- MPU: SSE intent is recorded at CreateMultipartUpload (including the SSE-C verification value) and applied once at Complete; SSE-C UploadPart / Complete must carry the same key throughout; read/write responses carry version/encryption headers.
- **Rotating the master key does not rewrite data** (acceptance ⑤): the DEK wrap lives in `xl.meta`, so as long as the key for the old `key_id` still exists it can be decrypted — rotation = add a larger `key-<n>.bin` to `OSS_KMS_DIR` (new writes use the new key, old objects still read); with the single-key-file provider, directly swapping the file makes old `key_id="file"` wraps undecryptable (**migrate to a KMS directory before rotating**).
- **Named CMKs and rotation (3.16)**: named rings live at `OSS_KMS_DIR/cmk/<name>/key-<n>.bin` (each ring rotates independently; the name is the path whitelist). Admin API: `GET/POST /api/v1/encryption/cmks` and `POST /api/v1/encryption/cmks/{name}/rotate` (admin-only). Rotation affects **new writes only** and old versions are retained for decryption (same stance as AWS KMS); audit records name/version/fingerprint only, never key bytes.
- **CMK delete and rewrap**: `DELETE /api/v1/encryption/cmks/{name}[?force=true]` scans local references first (any live reference → 409 with the list); a clean path atomically quarantines to `.cmk-trash`, waits for writers, rescans, then purges (restores on timeout/race). `POST /api/v1/encryption/cmks/{name}/rewrap` re-encrypts old-version objects to the current key version (dry-run by default; `apply/limit/cursor/bucket`), preserving bytes/ETag/version-id/metadata/tags with one meta flip; locked/tiered/no-SHA-256 versions are refused. **Limits**: reference scan and rewrap are local-node operations (run per node or offline `force`); bucket default-encryption configs are not scanned; no CLI; a failed purge may leave `.cmk-trash`. Old binaries reading CMK objects, a CMK bucket default, or an `sse-kms:<name>` MPU kind fail closed (500; rolling compatibility is not promised); every node must share the same KMS directory, and a node missing a CMK returns 4xx/5xx instead of degrading to plaintext.
- **Encrypted SK storage (M5)**: `access_keys.secret_key` is likewise envelope-encrypted (`enc:v1:` prefix, AAD domain separation, independent DEK per row; KMS directory preferred, single-key file as fallback) — **two write points** (console key creation, STS issuance) and **transparent migration on the read side** (existing plaintext rows are rewritten in place as ciphertext when read); in a cluster the ciphertext crosses the network and is decrypted at the consumer (plaintext SK never appears on the mesh). **Hard operational constraint**: multi-node must distribute the same master key; **removing the `OSS_MASTER_KEY_FILE`/`OSS_KMS_DIR` environment variables makes all existing ciphertext rows 500 (fail-closed)** — plan before changing. **Threat-model boundary (recorded)**: encryption only protects against **read-only** leakage (backups/snapshots/accidental copies); someone with write access to the database can insert their own plaintext SK to take over any AK (having DB write access before the slice was already full control, not a new surface).
- **Boundaries (recorded)**: bucket default encryption (`put-bucket-encryption`) is supported (a single SSE-S3/SSE-KMS rule; `aws:kms:<cmk>` references require the CMK to exist, SSE-C rejected); aetherupload internal ingestion is not encrypted (stored as plaintext); requesting a mode without the corresponding env → 500 (fail-closed, no silent plaintext); HTTP KMS is not implemented (the `KeyProvider` trait is the integration point; file-based KMS = multi-key directory).
- Section 18 of `tests/e2e_s3.sh` (landed with M5 wrap-up) covers live "write → HEAD header assertions → on-disk grep for plaintext signature strings".

## Object Lock (M5)

**Bucket level**: `CreateBucket` with `x-amz-bucket-object-lock-enabled: true` enables lock at creation (**automatically enables versioning**, AWS semantics); or for a versioning-enabled bucket, `PutObjectLockConfiguration` enables lock and sets a **default retention rule** (`Days`/`Years`, normalized to days, max 36500 days; `Enabled` can only turn on, not off — a second Put may only change the rule). The default rule applies to PUTs **without lock headers** (explicit lock headers take precedence, no stacking).

**Object-level headers** (PutObject / CopyObject target / CreateMultipartUpload; MPU records at create, applies at complete):

- `x-amz-object-lock-mode: GOVERNANCE | COMPLIANCE` + `x-amz-object-lock-retain-until-date` — must be **paired** and until in the future (otherwise 400); lock headers on a bucket without lock enabled → 400.
- `x-amz-object-lock-legal-hold: ON | OFF` — independent of retention.

**Deletion guard** (named version delete / batch delete / overwrite reclamation / console delete paths unified): `until ≤ now` (expired) may be deleted; not expired **COMPLIANCE always refuses (including admins)**; not expired **GOVERNANCE is only permitted with `x-amz-bypass-governance-retention: true`** (the caller must already be authenticated); **Legal Hold ON always refuses**. Refusal = 403 `AccessDenied` (batch delete records per key in the response `errors[]`, the rest are deleted). DELETE without a version id still writes a delete marker (locked versions naturally persist); lifecycle deletion likewise.
Legal Hold toggle API: `put/get-object-legal-hold` (`put` must name a version and **the bucket must have lock enabled**, otherwise 400; `get` is a metadata-surface read — SSE-C objects do not require the customer key).
Response surface: GET / HEAD return `x-amz-object-lock-mode` / `-retain-until-date` / `-legal-hold`.
**Policy actions**: `Get/PutObjectLegalHold` map to `s3:GetObjectLegalHold` / `s3:PutObjectLegalHold` (independent of `s3:GetObject`/`s3:PutObject`; AP policies must grant them explicitly). The direct S3 path follows the Read/Write gates (same axis as retention); non-admins need the corresponding permission; this is a permission-semantics change on 2026-10-23 and must be called out in the release notes.
**Anonymous boundary**: credential-less requests carrying any object-lock header (`x-amz-object-lock-mode` / `-retain-until-date` / `-legal-hold`) or `x-amz-bypass-governance-retention` are always 403 — anonymous policies have no expressible lock action, fail-closed.

**Retention**: `Put/GetObjectRetention` is wired (`versionId` required; COMPLIANCE cannot be shortened/cleared, GOVERNANCE shortening/clearing requires `x-amz-bypass-governance-retention`); the console object list shows retention / legal-hold status.
**Boundaries (recorded)**: the `buckets` table lock columns propagate via cross-node **row broadcast**; during the window non-versioned reclamation paths fail-closed and refuse deletion (strong consistency is deferred to M9, see "Known Limitations").

## STS Temporary Credentials (M5)

The standard STS protocol (Query/XML) is intercepted by s3s's front router (`POST /` + form encoding; **must be SigV4-signed**, does not override `check_access`). Two operations are supported:

```bash
# AssumeRole (the caller must be **admin** — the minimal model has no role trust policy, preventing sub-accounts from minting admin sessions to escalate;
# "role = user alias", ARN like arn:oss:iam::oss:role/<username>)
aws --endpoint-url http://127.0.0.1:9000 sts assume-role \
  --role-arn arn:oss:iam::oss:role/erik --role-session-name s1 --duration-seconds 900 \
  [--policy '{"Version":"2012-10-17","Statement":[...]}']
# GetSessionToken (derived from any long-term key, TTL 900..=129600 seconds, default 12h)
aws --endpoint-url http://127.0.0.1:9000 sts get-session-token --duration-seconds 900
```

- The response contains `AccessKeyId` (`ASIA…`) / `SecretAccessKey` / `SessionToken` / `Expiration`; temporary credentials are **usable cluster-wide** on the S3 surface (the session row fans out with the AK).
- **The session policy (only AssumeRole's `Policy` parameter, ≤4096B) intersects with user permissions**: it is layered **after** the three-tier table × bucket policy merge — session Deny → reject; **no match → reject** (not Allowed = rejected); a session can never elevate permissions. `DeleteObjects` applies the session decision per key too (prevents batch-delete bypass); the audit detail is suffixed with `;session:<allow|deny>`.
- **Expiry**: expired session row → `ExpiredToken` (long-term key expiry remains `InvalidAccessKeyId`); **one level of parent chain**: if the parent key (or parent owner account) is deleted/disabled/expired, the child is invalidated (the parent must be a long-term key; sessions cannot be parents).
- **Boundaries (recorded)**: the `SessionToken` itself is neither persisted nor validated (the AK is the credential — s3s's auth interface has no header surface, an AWS trust-chain difference); error responses use S3 error XML (not the STS `ErrorResponse` shape; the success path works directly with aws-cli); the GET query form (`?Action=`) is not accepted; out-of-range durations return 400 `InvalidArgument` (AWS uses `ValidationError`); sessions **only take effect on the S3 surface** (console/aether use JWT, no AK entry); expired session rows are not auto-cleaned (naturally unusable).
- **AssumeRoleWithWebIdentity**: disabled by default; enable with `[sts.web_identity]` (`issuer`, `audience`, local `jwks_file`, `max_duration_seconds`, `[[sts.web_identity.roles]]`). JWTs must be RS256/ES256 with strict kid/iss/aud/exp/nbf/iat, ≤16 KiB; RoleArn `role/<name>` must be an active existing user and `sub`/`email` values match exactly (no wildcards). Only this STS action is anonymous; others still require signing. JWKS rotation needs a restart, `email_verified` is not checked, and the anonymous endpoint should be rate-limited by a front proxy.

## Event Notifications (M6)

Bucket notification configuration goes through the S3 protocol (`PutBucketNotificationConfiguration` / `GetBucketNotificationConfiguration`); events are written to a local outbox (`event_outbox`, at-least-once) and then delivered by a worker. Only Kafka is supported as a target:

```toml
# oss.toml: static notification target configuration (id corresponds to the bucket config ARN)
[[kafka.targets]]
id = "t1"
brokers = ["127.0.0.1:9092"]
topic = "oss-events"
# Optional: TLS / SASL (SASL requires tls = true simultaneously; see the TLS section)
tls = false
# [kafka.targets.sasl]
# mechanism = "scram-sha-512"   # plain (default) / scram-sha-256 / scram-sha-512
# username = "..."
# password = "..."
```

```bash
aws --endpoint-url http://127.0.0.1:9000 s3api put-bucket-notification-configuration \
  --bucket bkt --notification-configuration '{
    "QueueConfigurations":[{
      "Id":"all","QueueArn":"arn:oss:sqs::t1:kafka",
      "Events":["s3:ObjectCreated:Put","s3:ObjectRemoved:Delete"],
      "Filter":{"Key":{"FilterRules":[{"Name":"prefix","Value":"logs/"}]}}
    }]}'
```

- Event-name whitelist: `s3:ObjectCreated:{Put,Post,Copy,CompleteMultipartUpload}` ·
  `s3:ObjectRemoved:{Delete,DeleteMarkerCreated}` · `s3:LifecycleExpiration:{Delete,DeleteMarkerCreated}` ·
  `s3:LifecycleTransition` · `s3:ObjectRestore:{Post,Completed}` ·
  `s3:ObjectAccessed:{*,Get,Head}` (read events see the next item).
  The event JSON is the AWS notification shape (`eventVersion 2.1`, `eventSource oss:s3`, urlencoded key, sequencer).
- Delivery semantics: **at-least-once** (steady state does not duplicate; crash windows may redeliver). Permanent errors (auth/protocol) >10 times go to the dead letter; connection-type errors are never abandoned (backoff capped at 300s). The topic must be **pre-created** (deployment prerequisite; UTOP does not judge death).
- Debug bypass without Kafka: `OSS_EVENT_SINK=file:/<dir>` (writes files, for testing); worker interval `OSS_EVENT_INTERVAL_SECS` (default 1; 0=off).
- Read access events: `s3:ObjectAccessed:*` / `:Get` / `:Head` are supported (only successful 200/206; 304/416/errors not emitted); other ObjectAccessed sub-operations (e.g. GetTagging) still 400; TLS/SASL see the TLS section.

## S3 Select (M6)

`SelectObjectContent` supports CSV / JSON (LINES/DOCUMENT) × output CSV / JSON, compression NONE/GZIP:

```bash
aws --endpoint-url http://127.0.0.1:9000 s3api select-object-content \
  --bucket bkt --key data.csv \
  --expression "SELECT s._1, s._2 FROM S3Object WHERE s._2 > 15 LIMIT 10" --expression-type SQL \
  --input-serialization '{"CSV":{},"CompressionType":"NONE"}' \
  --output-serialization '{"CSV":{}}' /tmp/out.csv
```

- SQL subset (anything outside the whitelist is `InvalidRequest`, no silently wrong results): `SELECT column|* FROM S3Object [s] [WHERE …] [LIMIT n]`; comparisons, AND/OR/NOT (SQL three-valued logic), BETWEEN/IN/LIKE/IS NULL, CAST; functions `substring/trim/lower/upper/char_length/abs/ceil/floor/round`; aggregates `count(*)/sum/min/max/avg` (no GROUP BY; aggregates must own the projection). CSV columns `s._1`; JSON paths `s.a.b`.
- Input: CSV delimiter/quote/escape/record delimiter/comment (default `#`)/header configurable; `AllowQuotedRecordDelimiter` defaults to false. ScanRange processes a whole record if its first byte falls within the range; End only = scan the last N bytes; GZIP/BZIP2 and ScanRange are mutually exclusive; JSON DOCUMENT does not support ScanRange. BZIP2 is supported for CSV/JSON input (multi-stream, budget on decompressed bytes). Parquet is mapped row-by-row to JSON objects (`s.col`/`s.a.b`); its request `CompressionType` must be `NONE` and ScanRange is rejected.
- Output: Records ≤256KiB chunks + Progress (about 1MiB cadence, `--request-progress`) + Stats + End; the three Stats counters are independent (`BytesScanned` raw/compressed, `BytesProcessed` fed to the evaluator, `BytesReturned` output).
- Limits/boundaries (recorded): object ≤256MiB; GZIP/BZIP2/Parquet decompressed ≤512MiB (fully buffered, no concurrency budget; Parquet uses row-group `total_byte_size`, page headers may transiently exceed it). BZIP2 is input-only (CSV/JSON); Parquet requires `CompressionType=NONE`; CRLF preserves `\r`; empty CSV fields into sum/avg return 400; LIKE pattern ≤4096 bytes.

## Bucket Replication (M6)

The source bucket must have **versioning Enabled**; targets use static `[[remotes]]` configuration, with rule `Destination.Bucket` written as `<remote-id>/<bucket-name>`:

```toml
[[remotes]]
id = "r1"
endpoint = "https://10.0.0.2:9000"  # http/https both supported; https see the TLS section
server_name = "s3.internal"           # optional: override when the certificate hostname doesn't match the endpoint
access_key = "..."                   # AK minted on the target instance
secret_key = "..."
region = "us-east-1"
max_bytes_per_sec = 1048576          # optional: outbound token-bucket rate limit (bytes/sec, ≥1024; unlimited by default)
```

```bash
aws --endpoint-url http://127.0.0.1:9000 s3api put-bucket-replication --bucket srcbucket \
  --replication-configuration '{"Role":"arn:oss:iam::oss:role/replication","Rules":[{
    "ID":"logs","Status":"Enabled","Filter":{"Prefix":"logs/"},
    "Destination":{"Bucket":"r1/dstbucket"},
    "DeleteMarkerReplication":{"Status":"Enabled"}}]}'
```

- Covers all write entry points: PUT / MPU complete / CopyObject / single and batch delete markers / aether ingestion / console delete / lifecycle delete. Objects additionally carry `x-amz-replication-status`: source `PENDING`→`COMPLETED` (any destination permanently failing beyond the limit → `FAILED`); target is `REPLICA` (loop prevention; REPLICA is not re-enqueued).
- Outbound is SigV4 + http1 PUT (`x-amz-replication-status: REPLICA` included in the signature); worker 300s lease + R1 graded retries (connection/408/429/5xx never abandoned, other 4xx permanent, >10 times dead letter); backlog is written to `repl_outbox` and automatically caught up after the target recovers. Interval `OSS_REPL_INTERVAL_SECS` (default 1; 0=off).
- Rate limiting uses an independent token bucket per remote (`[[remotes]].max_bytes_per_sec`); unlimited by default, zero change to old configs.
- Boundaries (recorded): target buckets/topics must be **pre-created**; SSE-C source objects cannot be replicated (customer keys never touch disk); version-specific delete and `Priority` have no effect (all destinations replicate); MPU source ETag is recomputed at the target (no ETag assertion); a single object is read fully into memory (≤16 concurrent); `Role` is not used for authorization.

## Multi-Site Replication (M7)

Two **single-node** instances establish a site pair and asynchronously replicate the control plane and versioned objects bidirectionally. `[site]` is the only switch (mutually exclusive with `[cluster]`; when unconfigured, site APIs are always 404):

```toml
[site]
name = "site-a"
region = "ap-east-1"     # validated consistent with the peer during pairing
priority = 10            # tie-breaking priority for same-second LWW
token = "<32–128 hex chars>"   # shared secret for the control-plane channel; auto-generated at first start if absent
```

```bash
# Admin surface: this site's identity (incl. token) → pair B on A (B must also pair A for bidirectionality)
curl -s $A/api/v1/site -H "authorization: Bearer $JWT"
curl -s -X POST $A/api/v1/sites -H "authorization: Bearer $JWT" -H 'content-type: application/json' -d '{
  "peer_id":"b","endpoint":"http://10.0.0.2:9000","region":"eu-west-1","priority":10,
  "s3_access_key":"<AK minted on B>","s3_secret_key":"<SK>",
  "peer_site_token":"<B's site token>"}'
curl -s $A/api/v1/sites/b/status -H "authorization: Bearer $JWT"   # lag/dead/outbox
```

- **Control plane**: changes to `buckets` (column-level versioning/owner/lock), `bucket_policies`, `permissions`, `users`, and long-term `access_keys` are written to `site_changelog` by SQLite triggers; the worker ships per peer by cursor (≤100 rows/batch, `OSS_SITE_INTERVAL_SECS` default 1s). Conflicts use LWW `(ts, priority, origin, seq)`: newer ts wins, same second by priority, then origin lexicographic; a local write older than the known clock is rejected by the BEFORE gate (409/500 until caught up). **Admin rows are not replicated**, STS session keys are not replicated.
- **Pairing snapshot**: `POST /sites` writes `sites` + cursor + five kinds of entity snapshots in a single transaction; the snapshot enters the local clock in the same transaction; only entities with "no row in the local clock or origin=this site" are snapshotted, avoiding mutual echo when pairing simultaneously.
- **Objects**: reuses `repl_outbox` (`target_kind='site'`), one row per peer; only versioned data writes and markers are enqueued, and deletion requires source bucket versioning=Enabled. Before sending, the worker signs `GET /{bucket}?versioning` (10s cache; 404/not Enabled → retryable); PUT passes through content-type and `x-amz-meta-*` and requires the target to return a real version-id (`null` → retry). Multiple targets for the same version aggregate PENDING→COMPLETED/FAILED.
- **Boundaries (recorded)**: peer addresses may be http/https (peer TLS see the TLS section); single-node site pairs; version UUIDs differ between the two ends and version-specific deletion is not replicated; deleting a non-empty bucket has no effect (row and data retained, recorded as dead letter); locks/tags/SSE are not replicated, SSE-C sources are permanent errors; AK ciphertext requires the same master key on both ends (pairing only verifies the vault switch is consistent, not the same key); the control plane is eventually consistent (no strong consistency, deferred to M9); endpoints/credentials stored in plaintext; `priority` only decides **same-second** ties (a low-priority new ts still beats a high-priority old ts — a deviation from the early spec's "decide by priority"); local control-plane changes during unpairing are not captured, and peer snapshots may overwrite these changes on re-pairing (entities that last won on the peer) — redo them after re-pairing; `x-amz-replication-status: REPLICA` can be supplied by any authenticated writer and can be used to suppress replication (the existing M6 trust surface; M7's DELETE loop prevention relies on the same header); when deleting a bucket, if the policy/grant rows' LWW clock updates, they are retained per L7, and recreating a same-named bucket may inherit these residual rows (cross-site concurrent delete/modify window).

## M8 Control Plane

The following are the implemented M8 capabilities and usage; design deviations and known boundaries see the end of this section and design doc §M8. Control-plane state is stored in SQLite `0003_m8.sql` (`access_points`/`olap_configs`/`jobs`/`job_tasks`/`inventory_configs`/`inventory_runs`/`tier_restores`), with **single-node single-process** semantics.

### Object Tagging and Copy Directives (P0, Complete)

```bash
aws --endpoint-url $E s3api put-object --bucket b --key k --body f \
  --tagging "env=prod&team=%E4%B8%AD%E6%96%87"
aws --endpoint-url $E s3api get-object-tagging --bucket b --key k
aws --endpoint-url $E s3api put-object-tagging --bucket b --key k \
  --tagging 'TagSet=[{Key=a,Value=1}]'
aws --endpoint-url $E s3api delete-object-tagging --bucket b --key k
# Copy two axes: REPLACE not provided means clear; a tagging header carried during COPY is ignored
aws --endpoint-url $E s3api copy-object --bucket b --key dst --copy-source b/src \
  --metadata-directive REPLACE --tagging-directive REPLACE --tagging "x=9"
```

Constraints: ≤10 tags; key 1..=128 / value 0..=256 (Unicode scalars); invalid → 400 `InvalidTag`; without a versionId the chain tail is used, chain-tail marker → 404, named marker → 405; tags do not propagate with replication/site.

### Job Engine and Batch Operations (S0/S3)

```bash
curl -s $E/api/v1/jobs/1 -H "authorization: Bearer $JWT"      # details + task pagination
curl -s -X POST $E/api/v1/jobs/1/pause -H "authorization: Bearer $JWT"
curl -s -X POST $E/api/v1/jobs/1/retry-failed -H "authorization: Bearer $JWT"
```

- Environment: `OSS_JOB_WORKERS` (default 2, 0=disabled), `OSS_JOBS_INTERVAL_SECS` (2), `OSS_JOB_MAX_ATTEMPTS` (3), `OSS_JOB_TASK_TIMEOUT_SECS` (900), `OSS_TIER_TASK_TIMEOUT_SECS` (3600).
- Claiming is by `priority DESC, next_at, task_no`; failures use exponential backoff (≤300s), reaching the limit records `PermanentFailure`; terminal batch jobs write `<report_prefix>/<job_id>/results.csv`.
- Single-node SQLite multi-worker; multi-process/multi-node unsupported (M9). M4 lifecycle **expiry deletion** still uses `sweep_once` and is not moved into this engine.

### Access Points and Object Lambda (S1/S2)

```bash
curl -s -X POST $E/api/v1/access-points -H "authorization: Bearer $JWT" \
  -H 'content-type: application/json' -d '{"name":"ap-one","bucket":"b","policy":{
    "Statement":[{"Effect":"Allow","Principal":{"AWS":"*"},
      "Action":"s3:GetObject","Resource":"arn:aws:s3:::b/*"}]}}'
aws --endpoint-url $E s3api get-object --bucket ap-one --key k out   # actually goes through /ap/ap-one/k
```

- Routing: path-style `/ap/<name>/<key>`; alias `<name>-s3alias` supports both the first path segment and the first Host label (`<name>-s3alias.<endpoint>`); unknown alias 404, no fallback to bucket routing. Standard SigV4 signatures cover the original path/host as usual. Bucket names reserve the `-s3alias` suffix (creation refused). **Upgrade note (L4)**: old buckets ending in `*-s3alias` created before M8 are shadowed by alias routing (first path segment / first Host label treated as an AP alias → 404); rename before upgrading and do not access via the original bucket name.
- **Upgrade note (L2, breaking)**: AP policies for object actions now match only object ARNs (`arn:aws:s3:::<bucket>/<key>` or the AP object ARN). Old policies granting `s3:GetObject` / `s3:PutObject` / `s3:DeleteObject` with a bucket ARN (without `/*`) change from "allow all objects" to "deny all" after upgrade (fail-closed); change them to object ARNs before upgrading.
- Authorization = identity/three-tier table/bucket policy/session policy **∩** AP policy (explicit Deny wins; AP has a policy but no match → deny); the CopyObject target axis uses `s3:PutObject`; audit is merged into one row. `DeleteObjects` layers the AP policy per key (denied keys `<Error>AccessDenied`, the rest still deleted; request body limit 1 MiB / 1000 keys). Object actions match only object ARNs (`arn:aws:s3:::<bucket>/<key>` and the AP object ARN); bucket ARNs only participate in bucket-level actions (same criteria as `policy.rs`, L2).
- **Authorized op = executed op (H1)**: `derive_op` uses a strict whitelist for query sub-resources (unknown/multiple sub-resources → 501), including `?legal-hold` → `Get/PutObjectLegalHold`; `x-id` must match the derived op (duplicate/inconsistent → 400); `Content-Type: multipart/form-data` POST is always rejected (s3s would parse it as PostObject, bypassing the query); after rewriting the request the op is derived again, inconsistency → 500 fail-closed. Normal Get/Put/Copy/List/MPU/DeleteObjects unchanged.
- AP policies are a strict subset: reject unknown fields / unknown condition operators / `NotAction` / `NotResource`; `Condition` only `IpAddress`/`NotIpAddress` + `aws:SourceIp` (IPv4/IPv6 CIDR, validated on save); Principal only `*` / AK / `uid:<n>`; invalid policies rejected with 400 on save, runtime load failure 500 (not treated as no policy). SourceIp peer comes from the connection address. Reverse-proxy deployments must set `OSS_AP_TRUSTED_PROXY=1` **and** make the direct TCP peer match `OSS_AP_TRUSTED_PEER_CIDRS` before `X-Forwarded-For`/`x-oss-source-vpc` are trusted; unset/unmatched peers, missing ConnectInfo, and malformed chains fail closed. Only the TLS `ReloadableHttpServer` path injects ConnectInfo — the plain-HTTP ecat listener cannot establish this trust chain. The rightmost-hop/`OSS_AP_TRUSTED_PROXY_HOPS`/`OSS_AP_TRUSTED_PROXY_CIDRS` chain rules still apply, and the reverse proxy must **overwrite** rather than pass through the client's own XFF. **When the IP condition cannot be evaluated: Deny statements match (fail-closed), Allow statements do not** — a missing peer will never silently let `Deny NotIpAddress` through.
- Supported: Get/Head/Put/DeleteObject, DeleteObjects, ListObjectsV2, ListObjectVersions, MPU Create/Complete/Abort/UploadPart/UploadPartCopy, CopyObject, Get/Put/DeleteObjectTagging, Get/PutObjectRetention, Get/PutObjectLegalHold, Get/PutBucketVersioning, HeadBucket, RestoreObject. Bucket lifecycle configuration, bucket default encryption, and Inventory configuration are control-plane / S3 bucket-level operations and **do not go through AP** (no corresponding shape on `/ap/...`, calling returns 501).
- Boundaries: no anonymous/cross-account/VPC endpoints/multi-node AP cache consistency; aws-chunked trailing checksums through AP do not forward trailing headers. **AP without a policy = no additional restriction** (identity/bucket policies still apply), unlike AWS's "access point without policy denies" (L3, recorded without changing behavior).

### Storage Classes, Tiering, and Restore (S4a/S4b)

- PUT/MPU Create/Copy accept `x-amz-storage-class`: STANDARD/STANDARD_IA/ONEZONE_IA/INTELLIGENT_TIERING/GLACIER/GLACIER_IR/DEEP_ARCHIVE/REDUCED_REDUNDANCY; unknown or **archive-class direct write** → 400 `InvalidStorageClass`. HEAD/GET/List/Versions read back the storage class (None=STANDARD).
- `Version` gains `storage_class` / `tier` (`backend/key/size/etag/sha256/phase/archived_at/restore_expires_at`); the local shard view for Archived/Restoring is empty, GET/Range → 403 `InvalidObjectState` (HEAD can still read metadata); fsck does not report missing shards.
- Deleting an archived version returns `TierRef` via `DeleteOutcome`, and `TierGcSink` cleans the remote side (real tier backends and Transition/Restore are in S4b).
- Boundaries: storage class/tags do not propagate with M6/M7 replication; archived objects must be read within the same version's binary.

### Object Lambda (S2, Read-Only Transform)

```bash
# Configure the transformer (owner/admin); kind=http, endpoint trusted by the admin
curl -s -X PUT $E/api/v1/access-points/ap-one/transform \
  -H "authorization: Bearer $JWT" -H 'content-type: application/json' \
  -d '{"kind":"http","endpoint":"https://olap.example.com/transform","timeout_ms":5000,"max_response_bytes":67108864}'
aws --endpoint-url $E s3api get-object --bucket ap-one --key k out   # actually GET /ap/ap-one/k
```

- ABI: `POST <endpoint>`, body = raw object bytes; headers `x-oss-bucket/version-id/etag/size/key-b64`; the response body is the transformed bytes, `Content-Type` may be overridden; `Content-Length`/`ETag` are recomputed from the transform result.
- Only transforms the GET object body; HEAD passes through, write operations 405. Conditional headers 304/412 pass through; Range → 400; output fully buffered.
- Limits: input `OSS_OLAP_MAX_INPUT_BYTES` (default 64 MiB), output `max_response_bytes` (default 64 MiB, max 1 GiB), `timeout_ms` 1–30s, 16 concurrent per process; HTTP only http/https, rejects private/reserved addresses and redirects, each resolution is pinned (SSRF defense).
- WASM: `{"kind":"wasm","module_b64":"..."}` (module ≤16 MiB, compiled on save); must be built with `--features olap-wasm`, otherwise saving returns 400 "not enabled", and GET will not silently pass through.
- Boundaries: no write transforms; no dry-run for configuration; transformer failure → GET 500 (does not return the original).

### Batch Operations (S3)

```bash
# 1) Manifest: CSV inside an object bucket, header bucket,key[,versionId] (BOM/CRLF tolerated)
# 2) Create job (JWT); operation = CopyObject|DeleteObject|ReplaceTags|RestoreObject|InvokeLambda
curl -s -X POST $E/api/v1/jobs \
  -H "authorization: Bearer $JWT" -H 'content-type: application/json' -d '{
    "kind":"batch","manifest_bucket":"b","manifest_key":"manifest.csv",
    "operation":"ReplaceTags","tags":{"env":"prod"},
    "report_bucket":"reports","report_prefix":"batch/run1","priority":0}'
# → 201 {"job_id":1,"total":1001}
curl -s $E/api/v1/jobs/1 -H "authorization: Bearer $JWT"   # {"job":{state,total,succeeded,failed,…},"tasks":[…]}
curl -s -X POST $E/api/v1/jobs/1/retry-failed -H "authorization: Bearer $JWT"  # → {"job_id":2}
```

- Task actions: Copy follows Copy semantics (target bucket/prefix, REPLACE metadata/tags); Delete clears tier refs; ReplaceTags replaces tags wholesale; Restore goes through S4b restore; InvokeLambda supports HTTP transformers, and WASM when built with `olap-wasm` (output discarded).
- Quotas: `OSS_JOB_MAX_INFLIGHT_PER_USER` (100) / `OSS_JOB_MAX_INFLIGHT_GLOBAL` (1000); per-row authorization at creation (deduplicated), manifest/task limits see error messages.
- Report: `<report_prefix>/<job_id>/results.csv`, fixed columns `taskId,bucket,key,versionId,resultCode,resultString,startTime,endTime`; only started tasks enter the report; `Succeeded`/`PermanentFailure`; time `%Y-%m-%dT%H:%M:%SZ`.
- `retry-failed` creates a sub-job (`parent_job_id`, only failed tasks), the parent report is not rewritten; no failed items → 409.
- **Preemption**: when capacity is full and the **same submitter** has a strictly higher-priority job with ready tasks, lower-priority running jobs are marked `preempted`; this happens only at the claim→execute safe boundary (in-flight actions are not interrupted), unexecuted tasks are requeued without consuming attempts or duplicating side effects, and jobs return to `queued` after the high-priority queue drains. Priority is clamped to `-100..=100` (out-of-range → 400); preemption never crosses submitters (cross-tenant DoS guard). Cooperative/single-node, default 2s scheduler; disabled when `OSS_JOB_WORKERS=0`.
- **Cross-account manifests**: non-admin owners may only use a manifest bucket in their own derived account with read access; admins may cross accounts; authorization runs before HEAD/GET and bucket-policy Deny still binds admins.
- Boundaries: job terminal states `done`/`error`/`cancelled` (any failure means `error`), plus runtime `preempted`; the console Jobs page does not yet render `preempted`.

### Inventory (S5)

```bash
curl -s -X PUT $E/api/v1/buckets/b/inventory -H "authorization: Bearer $JWT" \
  -H 'content-type: application/json' -d '{
    "id":"inv1","is_enabled":true,"frequency":"Daily",
    "destination_bucket":"reports","destination_prefix":"inv","format":"CSV",
    "filter_prefix":"","included_object_versions":"All",
    "optional_fields":["ReplicationStatus","EncryptionStatus"]}'
curl -s -X POST $E/api/v1/buckets/b/inventory/inv1/run -H "authorization: Bearer $JWT"
# → 202 {"run_key":"manual-<epoch>","job_id":3}
aws --endpoint-url $E s3 cp \
  s3://reports/inv/b/inv1/manual-<epoch>/manifest.json - | head
```

- Scheduling: Daily (UTC date)/Weekly (ISO week), worker `OSS_INVENTORY_INTERVAL_SECS` (default 60, 0 disables); same-slot uniqueness dedup, after downtime only the most recent slot is made up; force-run for testing/ops (owner/admin).
- Output: `<dest_prefix>/<source_bucket>/<config_id>/<run_key>/manifest.json` + `data/<uuid>.csv.gz` (CSV) or `data/<uuid>.parquet` (Parquet); the manifest contains `sourceBucket/destinationBucket/version/fileFormat/fileSchema/files[]`, and `files[]`'s `size`/`md5Checksum` are the on-disk file byte size and MD5 (base64, aligned with AWS v1).
- Parquet: a low-level writer without Arrow dependencies, SNAPPY compression, 8192 rows/row group; column names use AWS Inventory's lower_snake_case (`bucket,key,version_id,is_latest,is_delete_marker,size,last_modified_date,e_tag,storage_class,...`), `last_modified_date` is TIMESTAMP_MILLIS; `fileSchema` is the Hive/Athena-readable Parquet schema text.
- Hive manifest: each run also writes `<run_key>/hive/dt=YYYY-MM-DD-HH-MM/symlink.txt` (UTC), containing one line `s3://<dest>/<data_key>`, for Athena SymlinkTextInputFormat; it is subject to the target bucket's default encryption like the data/manifest. CSV and Parquet share this manifest.
- Columns: 9 required columns `Bucket,Key,VersionId,IsLatest,DeleteMarker,Size,LastModifiedDate,ETag,StorageClass`; 6 optional columns appended in fixed order `ReplicationStatus,EncryptionStatus,ObjectLockRetainUntilDate,ObjectLockMode,ObjectLockLegalHoldStatus,ChecksumAlgorithm`.
- Accounts (3.7): the config records the source bucket's 12-digit account at write time (storage-JSON extension `ossSourceAccountId`; legacy configs derive it from the current bucket account). The optional `destination_account_id` (console field; `AccountId` on the S3 wire) must be 12 digits and equal the destination bucket's current account. A **cross-account destination** (source and destination bucket accounts differ) may only be configured by an admin (non-admins get 403 even with `PutObject` on the destination); every run revalidates both accounts and fails closed without writing on drift. Writes still go through the config owner's `PutObject` check, so existing authorization is not bypassed. The destination bucket field accepts a bucket name or `arn:aws:s3:::<bucket>` (normalized to the bucket name). Account = user namespace v1, **not tenant isolation**.
- The manifest adds `accountId` (source bucket account) and `destinationAccountId` (destination bucket account) alongside the standard fields.
- Boundaries: full scan by default (incremental is the node-local 3.6 mode, not CDC), single data file (≤5 GiB), CSV/Parquet; `IsMultipartUploaded`/`IntelligentTieringAccessTier` unsupported; optional columns may HEAD each version.

### Tiering Transition and Restore (S4b)

```toml
# oss.toml: remote S3-compatible tier (kind default = s3)
[[tiers]]
id = "t1"
kind = "s3"
endpoint = "http://127.0.0.1:40125"   # http/https
bucket = "cold"
access_key = "TIERAK"
secret_key = "TIERSK"
region = "us-east-1"

# Local cold-drive pool: persists to <path>/<tier_id>/<bucket>/<version_id>/<raw key>;
# same-directory temp file + fsync + rename, path segments reject absolute paths/`..`/NUL.
[[tiers]]
id = "local1"
kind = "local"
path = "/var/lib/oss/cold"
```

```bash
# Lifecycle transition to GLACIER (days=0 = satisfied immediately on the next sweep; tier resolved and persisted at write time)
aws --endpoint-url $E s3api put-bucket-lifecycle-configuration --bucket b \
  --lifecycle-configuration '{"Rules":[{"ID":"cold","Status":"Enabled","Filter":{"Prefix":""},
    "Transitions":[{"Days":0,"StorageClass":"GLACIER"}]}]}'
aws --endpoint-url $E s3api get-bucket-lifecycle-configuration --bucket b   # read-back round-trip
curl -s -X POST $E/api/v1/tiers/sweep -H "authorization: Bearer $JWT"      # {"queued":n}
curl -s $E/api/v1/tiers -H "authorization: Bearer $JWT"                    # [{id,kind,path,endpoint,bucket,healthy}]
# Remote GC/reconciliation: dry-run by default; real deletion requires explicit dry_run=false
curl -s -X POST $E/api/v1/tiers/gc -H "authorization: Bearer $JWT" \
  -H 'content-type: application/json' -d '{"dry_run":true,"grace_days":7}'
curl -s -X POST $E/api/v1/tiers/gc -H "authorization: Bearer $JWT" \
  -H 'content-type: application/json' -d '{"dry_run":false,"tier":"t1","grace_days":7,"max_deletes":1000}'

aws --endpoint-url $E s3api head-object --bucket b --key k                 # StorageClass=GLACIER
aws --endpoint-url $E s3api get-object --bucket b --key k out              # 403 InvalidObjectState
curl -si --aws-sigv4 "aws:amz:us-east-1:s3" --user "$AK:$SK" \
  -X POST "$E/b/k?restore" -H 'x-amz-restore-request: days=1'              # 202 + ongoing-request="true" (see below)
aws --endpoint-url $E s3api get-object --bucket b --key k out              # readable after restore completes
aws --endpoint-url $E s3api delete-bucket-lifecycle --bucket b
```

- Lifecycle rules can also be configured via the console `GET/PUT /api/v1/buckets/{b}/lifecycle` (`transition_days/transition_class/transition_tier`); S3 and console share the same validation, PUT replaces in full.
- Transition is scanned periodically by `OSS_TIER_SWEEP_INTERVAL_SECS` (default 3600) + admin force-sweep; deduplicated by object, only the current non-encrypted non-tiered version, ≤10000 objects per run; fully in-memory transfer (single object ≤ `OSS_TIER_MAX_BYTES`, default 1 GiB).
- Restore: body XML `<RestoreRequest><Days>n</Days></RestoreRequest>` or `x-amz-restore-request: days=n[,tier=]`, days 1..=36500 (default 1); returns HTTP 202 + `x-amz-restore: ongoing-request="true"`; HEAD three states (Archived no header / Restoring / Restored `ongoing-request="false", expiry-date=…`). s3s 0.17's generated RestoreObject code always serializes 200 OK and discards `S3Response.status`; router-layer middleware rewrites the POST `?restore` 200 to 202 (error statuses and other requests pass through as-is).
- Expiry reclamation: reaper `OSS_TIER_REAPER_INTERVAL_SECS` (default 300), accuracy about 300s; after expiry it returns to Archived (GET 403 again). At startup it reconciles pending/restored rows with Version.
- Local cold-drive pool (`kind = "local"`): `put` writes a same-directory `.<name>.tmp-<uuid>` + `fsync` + `rename`, validates MD5 (when ETag is 32-hex); `head` returns an error when the root directory is missing (console health false); after startup it can directly read back already-persisted objects and clean up same-directory crash leftovers; `delete` deletes empty directories bottom-up.
- Remote GC/reconciliation (`POST /api/v1/tiers/gc`, admin only): list the remote first, then full-scan local version meta; any list/scan failure aborts the whole round without deleting; live `TierRef`s are never deleted; only objects within the `<tier_id>/` prefix and age ≥ `grace_days` (default 7) are deleted; at most `max_deletes` per round (default 1000); deletion failures are returned per item and retained for the next round; `missing_live` only indicates a live reference is missing on the remote and writes no data. `dry_run` defaults to true.
- Boundaries: tier supports remote S3 and local cold-drive pools; fully in-memory transfer; no automatic scheduled GC (must be explicitly triggered by an admin); remote deletion remains best-effort, failures leave orphans for GC retry; SSE objects are not Transitioned; archived object replication/site replication is unavailable (Restore first).

### M8 Known Boundaries (Recorded)

1. Control plane single-node: AP cache, job engine, Inventory scheduling, tier reaper are all single-process; sharing SQLite across nodes is unsupported. The 11 control tables such as IAM/bucket/policy are strongly consistent via M9 Raft in `[site]+[raft]` mode; other M8 state remains single-node.
2. AP supports `/ap/<name>` and `<name>-s3alias` (path/Host); no anonymous/cross-account/VPC endpoints; ListBuckets/Create/DeleteBucket unsupported. **AP without a policy = no additional restriction** (unlike AWS's default deny, L3); old `*-s3alias` buckets are shadowed by alias routing and must be renamed before upgrading (L4, see the access points section).
3. Object Lambda is read-only GET; WASM is off by default; output fully buffered; endpoint trusted by the admin (still rejects intranet SSRF).
4. Batch supports cooperative priority preemption (safe action boundaries, no duplicate side effects) and cross-account manifest authorization (non-admins limited to same account + read; admins may cross accounts; authorization before HEAD/GET, bucket-policy Deny still binds admins); InvokeLambda supports HTTP (`olap-wasm` builds also support WASM); actions emit bucket notifications per the object's bucket (Copy→target `CreatedCopy`, Delete→`RemovedDelete`/`DeleteMarkerCreated`, Restore→`RestorePost`; ReplaceTags/InvokeLambda have no matching S3 event and emit none) and still emit replication/clear tier. The console does not render `preempted` yet.
5. Inventory full scan by default (incremental is the node-local 3.6 mode), CSV/Parquet single data file; cross-account destinations are admin-only to configure (source/destination accounts revalidated every run); the Hive compatibility surface is only `symlink.txt` (no Athena table creation/partition auto-discovery).
6. Tiering supports remote S3 and local cold-drive pools, fully in-memory transfer; S3 lifecycle already supports tag/size/And Filter, Expiration.Date/ExpiredObjectDeleteMarker, Transition.Date, multiple transitions, noncurrent expiration/transition; still does not support AbortIncompleteMultipartUpload (needs an MPU index, 501).
7. Archived objects are bound to the same version's binary; a full upgrade is required before enabling Transition. Tier remote deletion is best-effort; GC/reconciliation is only explicitly triggered by an admin (dry-run by default), no automatic scheduled GC; restore expiry accuracy about 300s.
8. Job states in the DB `done/error` (mapped to Completed/Failed); unexecuted tasks on cancellation do not enter the report; CSV does not do formula escaping.
9. RestoreObject's 202 is written by router-layer middleware (s3s 0.17 generated code discards `S3Response.status`); the recognition criterion is POST + `restore` query sub-resource.
10. v1.19.0 adds the `m8.runstate` OSSCTL3 extension: the nine runtime tables can be exported/installed with snapshots and semantically validated, but schedule leases, command producers, worker takeover and the multi-node runtime (Tasks 5–13) are not delivered; the control plane remains single-node single-process.

## M9 Strong Consistency

`RAFT_READY=true`, `SYNC_READY=true`, `STRETCH_READY=true` in `crates/oss-server/src/raft/mod.rs` determine runtime gating (capability bits also require the corresponding configuration to exist). `GET /api/v1/raft/status` reports the real state (`enabled/node_id/role/leader/term/applied/lag/stale/snapshot/purged/voters/learners/production_ready`, plus `wire_version` / `feature_level` (1..=3) / `activation_level` / `effective_feature_level` and `compat.{min_wire_version,min_membership_wire_version,peers,mixed,blocked_reason}`; when `voters<3`, `production_ready=false`). `lag` = `last_log_index - last_applied.index`, i.e. the number of log entries appended locally but not yet applied (no value treated as 0; **not** the gap to the leader, unreceived logs are not counted); `stale` = this node is not leader and `lag>0`, only indicating that this node has appended-but-unapplied logs. A follower's read is its locally applied state, **not** a linearizable read; during partitions/disconnects `lag` may still be 0, and **`stale=false` does not mean caught up with the leader**, nor is it a freshness guarantee. `/api/v1/site/raft/*` provides append/vote/snapshot/status/membership/write/join.

### Witness Deployment

The production shape is **3 voters: two data sites A/B + C witness**, quorum 2; any two votes can commit, and A+B, A+C, B+C can all write. C only persists `raft.db` + the control-plane `state_db` (11 control tables), **does not build a Store, does not provide S3/console/object worker, stores no object data, and is not in the `sites` table**; sync gating's "exactly 1 data peer" counts by `sites` rows and is unaffected by C. C catches up control state via snapshots.

| Node | Raft `node_id` | Role | Key config/responsibilities |
|---|---|---|---|
| A (data site) | 1 | voter, `bootstrap=true` | `[site]`+`[raft]`; writes objects; `advertise_endpoint=http://a:9000` |
| B (data site) | 2 | voter, `bootstrap=false` | `[site]`+`[raft]`; writes objects; waits to join via leader/pairing |
| C (witness) | 3 | witness, `bootstrap=false` | standalone `witness.toml`: `node_id/advertise_endpoint/cluster_token/db_path/state_db`; control plane only |

The startup path is `oss-server witness --config witness.toml` (`WitnessToml` + `Db::connect_witness`, no Store/S3 construction; HTTP only exposes `/health*` and `/api/v1/site/raft/*`). Membership flow: A initializes `{A}` → console `POST /api/v1/sites` pairs B (on A: `add_learner(B, blocking)` then `change_membership({A,B})`; on B: `/join` writes the local `sites` row) → `raft-add-witness --config a/oss.toml --node-id 3 --endpoint http://c:PORT` lets C catch up via snapshot and join as the 3rd voter; the membership set follows `metrics().membership_config`, not a hardcoded `{A,B,C}`. C can be elected leader; a follower's membership changes/control writes are single-hop forwarded to the leader via `x-oss-raft-forwarded`.

### Sync Write Semantics

Production configuration (A/B paired as 2 voters; 3 voters after adding witness C):

```toml
[site]
name = "A"
region = "r1"
token = "<32–128 hex chars>"

[raft]
node_id = 1
role = "voter"
bootstrap = true
feature_level = 1                      # Level B rolling upgrade; default 1, range 1..=3 (see runbook)
advertise_endpoint = "http://a:9000"   # main HTTP; not the mesh port
cluster_token = "<shared cluster token>"
db_path = "/var/lib/oss/raft.db"       # Raft runtime requires an explicit path; current config loading does not enforce (RaftToml.db_path optional)

[sync]
max_object_bytes = 67108864            # default 64 MiB; exceeded before staging → 400
timeout_ms = 10000                     # default 10s; sync remote calls only → timeout 503
```

- **Creation prerequisites (since S6)**: sync buckets require `[raft]` + `RAFT_READY` + exactly 1 data peer; creation sets `versioning=Enabled`, and `replication_mode` is immutable after creation. `SYNC_READY=true`: S3-surface `x-oss-replication-mode: sync` and console bucket creation both go through Raft commit (single-node or 3-voter both work). Sync buckets reject object lock (409), SSE-C (400), Tagging API (501) and lifecycle Transition (400, only Expiration allowed); `Suspended` versioning is rejected on sync buckets (`InvalidBucketState`).
- **Same origin version id**: a local version UUID is pre-generated before commit; the remote token PUT carries the signed header `x-oss-origin-version-id`. The receiver, under a sync bucket + valid `x-oss-site-token`, adopts that UUID as `Version.version_id` and writes `Version.remote_version_id=Some(uuid)`; the response `x-amz-version-id` must equal that UUID, otherwise 502 `sync version id mismatch` and no local commit. The receiver idempotently returns the existing version for the same key/version id/size/ETag replay, 409 if different. Non-token M6/M7 `REPLICA` ingestion keeps the old behavior and does not adopt this rule.
- **Remote-first write order (PUT/MPU Complete/Copy)**: local staging invisible → during assembly/staging write a plaintext tee (`<data_dir>/.oss.sys/tee/<uuid>.plain`, mode 0600) → write `sync_write_intents` (`state=remote_pending`, `PRAGMA synchronous=FULL`) → remote token PUT (requires 2xx and the same id) → local meta commit → clean up intent + tee. Remote unreachable/timeout/5xx → 503 (remote deterministic 4xx preserve 400/409 semantics), no local meta; local commit failure → token DELETE same-id compensation; kill -9 between the remote ack and local meta → recovery only does **compensation** (if local meta does not exist delete the remote same-id, if it exists just clear intent/tee), **never resume commit from the tee**; when the remote is temporarily unreachable the intent is retained and retried. MPU tee is written once when Complete assembles the part stream; missing tee → 500; the tee cannot rebuild MPU ETag/metadata. Orphan tees without an intent older than **1 hour** are deleted by startup/periodic cleanup; those with an intent go to the recovery worker (runs once at startup, then every 30s; only processes rows older than `timeout + 60s` to avoid touching in-flight ones).
- Metadata replication of content-type/user-metadata/tags/storage-class; checksums for PUT/MPU are recomputed remotely, CopyObject inherits the source object checksum (`x-amz-checksum-*`) and passes it through the sync gate PUT and into SigV4 SignedHeaders; when the source has no checksum the target does not fabricate one; HEAD checksums on both A/B sides match. SSE-S3/KMS is decided locally by the target. The default 64 MiB / 10s requires about ≥52 Mbps uplink; when WAN bandwidth is insufficient, lower `max_object_bytes` or raise `timeout_ms`; the defaults target small objects/compliance buckets.

### Sync Delete Semantics

- **Single entry point**: S3 `DeleteObject`/`DeleteObjects`, lifecycle Expiration, Batch Delete, console object/bucket deletion all go through `SiteSyncDelete`; sync buckets are remote-first (remote ack first, then local), async/M7 buckets keep the original store path.
- **Internal token routing** (JWT-exempt, `x-oss-site-token` constant-time comparison, missing/wrong 403; local operations only, never forwarded): `POST /api/v1/site/delete-object` (version/`marker_id`/`all_versions`), `HEAD /api/v1/site/head-object` (200 exists / 405 delete marker / 404 does not exist), `GET /api/v1/site/bucket-empty`, `POST /api/v1/site/bucket-quiesce`, `POST /api/v1/site/delete-bucket`. A normal S3 `DELETE` never carries this token and always goes client-side remote-first; a proxy stripping the token only makes the internal route 403 and does not degrade to the client path.
- **Named version**: the local version id is the remote id; the internal route idempotently returns 204 for a non-existent version. If a pre-M9 object has no `remote_version_id` or the mapping is inconsistent → 409, with a message suggesting `sync-reconcile --repair` (see below).
- **DeleteObject (no versionId)**: pre-generate a marker UUID, create the same-id marker remotely first, then locally; the retry contract is **at-least-once**: object invisibility is idempotent, but `ListObjectVersions` may show multiple delete markers.
- **DeleteObjects**: per-key remote-first; remote unreachable/timeout/5xx → **whole request 503** (successful keys are already committed, the client will not receive per-key 200+Error results), the metric `oss_sync_delete_partial_total` increments; remote deterministic 4xx (400/409) are kept as per-key `Errors`. "Idempotent" only means object invisibility/same-id version deletion, not that the marker list is item-by-item identical.
- **Delete bucket**: set `deleting=1` → wait for local active writers to reach zero (30s cap) → remote `bucket-quiesce` (the remote likewise waits 30s for its own writers) → both ends `bucket-empty` → remote `delete-bucket` → local delete. Non-empty/timeout → roll back deleting + 409/503; on failure, keep deleting and the `delete_bucket` intent for periodic retry. PUT/MPU Complete/Copy/Delete during deletion → 503 (MPU initiate/UploadPart are not intercepted).
- **Delete intent recovery**: `sync_delete_intents` has one UUID row per operation, pending before the remote call, done after ack, deleted after local success; 30s worker + first round at startup. `remote_pending` uses three-state HEAD: 200/405 → the remote still exists, retry the internal delete; 404 → already gone, delete locally; `remote_done` just fills in locally.
- **`sync-reconcile [--repair]`**: read-only mode reports missing mappings/missing remote objects; `--repair` re-pushes readable plaintext (≤ `[sync].max_object_bytes`) by local version id, refreshes `remote_version_id`, cleans old-site `sync_*_intents` and `repl_outbox(target_kind='site')`, and only clears `sites.reconcile_required` after everything succeeds (before B′ replacement this flag makes sync writes/deletes always 503). Encrypted/oversized/conflicting objects report an error and keep the gate, exit code 1. Read-only mode only reports (`markers_missing` is the number of remote missing markers). `--bucket B` only scopes scanning/diagnostics, **does not clear** the site-level gate/intents/outbox; clearing the gate requires a full-database run. Usage: `oss-server sync-reconcile [--repair] [--bucket B] [--json] --config a.toml` (offline `Db::connect_offline` + `Store::open`, does not load AppState/open raft.db; stopping the service is recommended to avoid concurrent object directory writes).

### stretch 2×6 (Data Plane + Raft Control Plane Wired)

Target configuration (one copy per data site, C witness configured separately; common items like `listen`/`data_dir(s)`/`database_url` omitted, this site must have exactly 6 `data_dirs`):

```toml
[site]
name = "A"
region = "r1"
token = "<64 hex>"

[stretch]
node_id = "A"
self_addr = "a:9100"          # this site's mesh gRPC; independent of main HTTP
peer_node_id = "B"
peer_addr = "b:9100"
peer_drives = 6
placement = "v2"
mesh_secret = "<A/B shared>"
mesh_timeout_ms = 5000

[ec]
enabled = true
data = 8
parity = 4
inline_threshold = 0          # stretch forces 0

[raft]
node_id = 1                   # A=1,B=2,C=3 (target 3-voter)
role = "voter"
bootstrap = true
advertise_endpoint = "http://a:9000"
cluster_token = "<shared cluster token>"
db_path = "/var/lib/oss/raft.db"
```

- **Topology**: exactly 2 data sites × 6 drives = 12 slots, EC 8+4, `placement="v2"`; each site has exactly 6 shards, meta mirrored 12 copies. `Q_s=data+1=9`; a single site's 6 slots < 9, **both sites must be fully present for reads and writes**, a single-site failure returns non-2xx (500/503), **no site disaster tolerance is promised**, and there is no "single-site degraded read".
- **Data path**: `self_addr` is a real `xl_client::serve` mesh gRPC listener (not a test harness), and must use a different port from the main HTTP/`advertise_endpoint`; `peer_addr` is the peer mesh. Cross-site: one RPC per 64 KiB block per remote shard; WAN latency/bandwidth directly limits throughput, only suitable for small objects/compliance objects; adjust with `mesh_timeout_ms`.
- **inline=0**: object bytes only land in shards, not in `xl.meta`; meta still contains key/tags/user-metadata/content-type.
- **M7 async site replication disabled**: `repl_outbox` with `target_kind='site'` must always be 0; any stretch startup finding leftover rows refuses to start; M6 rule replication (external remote) remains usable. Creating sync buckets under stretch returns 400; first enabling also requires a brand-new empty DB (`buckets=0`, each `data_dirs` contains only `.oss.sys`, no sync buckets), after passing it writes `stretch_initialized`, and normal restarts no longer require an empty DB; **in-place migration is not supported**. `[stretch]` is mutually exclusive with `[cluster]`/`[[groups]]`. When unpaired (local `buckets` row count 0), a Raft startup **skips bucket directory reconciliation**, avoiding isolating peer-owned directories as orphans; after pairing, a normal restart performs full reconciliation.
- **Single-drive failure**: EC 8+4 can rebuild within a site, but `Q_s=9` still requires at least 9 slots reachable; after site recovery use `fsck --repair`/`heal` to repair missing shards through the mesh.

### Feature Levels 1..3 and OSSCTL3 (v1.19.0 foundations)

`[raft].feature_level` ranges over 1..=3 (default 1). Levels only increase; activation writes `schema_meta.raft_feature_level`, and startup refuses a marker above the configured/binary maximum.

| Level | Snapshot format | Contents it can carry | Status |
|---|---|---|---|
| 1 | OSSCTL1 | Existing 11 control tables | Available |
| 2 | OSSCTL2 | Structured lifecycle `config_json` | Available |
| 3 | OSSCTL3 | Accounts/members, `m8.runstate` extension, `ControlCommand::Ext` | Foundations/preview |

OSSCTL3 = OSSCTL2 + `extensions` (names `[a-z0-9._-]{1,64}`, at most 64 entries, ≤64 MiB decoded total). `required_feature_level` follows the data: account rows or non-empty extensions → 3, `config_json` → 2, otherwise 1; a lower-level install rejects higher-level data. `ControlCommand::Ext` uses `type_id` + payload; the leader rejects unregistered/empty/typo'd type IDs before append. **The production registry is empty** — there is no usable product-level Ext command; the 24 MiB command cap still applies and apply is fail-stop. An OSSCTL3/level-3 environment cannot roll back to v1.18 or earlier.

### Tenancy Foundations (v1.19.0 preview)

Migrations 0005/0006 add `accounts`/`account_members`/`account_usage` and the canonical marker `schema_meta.accounts_canonical_v1`; OSSCTL3 `ControlData` adds `accounts`/`account_members` (serialized only when non-empty). On install: feature<3 rejects account rows; a DB carrying the canonical marker rejects level-2 installs (the marker cannot be cleared by downgrading); export/cutover/force-recover validate provenance. Snapshot reads are gated on the canonical marker: without it, account rows are excluded from snapshots (so node-local derived rows cannot be exported and diverge elsewhere).

Standalone (non-Raft) startup automatically runs backfill v1 and v2 (v2 removes global admins from the member table and deletes their member-less derived accounts; their buckets belong to the system account); the marker is idempotent. **Not delivered**: Raft account commands, the canonicalization worker, and Tasks 4–12 account APIs/quota/console; under `[raft]` tenancy is read/foundation only and accounts cannot be managed. The v1.18 standalone account MVP (`accounts_api.rs`, 503 under Raft) is unchanged.

### M8 Run-State Snapshots (runstate, v1.19.0 preview)

The nine runtime tables (jobs/job_tasks/inventory_runs/inventory_cursors/inventory_incremental/tier_restores/lifecycle_cursors/schedule_lease/runstate_meta) are exported/installed as the `m8.runstate` OSSCTL3 extension (base64 JSON envelope, ≤64 MiB, unknown fields rejected). Install validates semantics first (next IDs above max IDs, non-empty tables seeded, no dangling parent_job_id/job_task/inventory_run/tier_restore references), then deletes and inserts the nine tables in one savepoint; snapshots carrying the extension require feature 3. **Not delivered**: schedule leases, command producers, worker takeover and the multi-node runtime (Tasks 5–13); the control plane is still single-node single-process, and runstate only guarantees export/install consistency.

### cutover / force recovery runbook

Hard constraint: **manually editing the old `raft.db` is forbidden**; the new cluster never writes the old epoch.

**M7 → Raft cutover** (switching two M7 DBs to the control-plane Raft):

1. Stop A/B; `oss-server raft-export --config a/oss.toml --out /backup/export.json` (11 replication tables, natural keys; `--witness` exports only the witness's `state_db` (control-plane 11 tables only, no objects); that export cannot be used for cutover; it can be used for force recovery, with object data still restored from backups).
2. For each M7 target DB, dry-run first: `raft-cutover --config x/oss.toml --from export.json --dry-run`; after no conflicts, drop `--dry-run`. Conflicts are reported **field-by-field per natural key of the 11 tables** (the CLI prints one line `conflict <table> <key> <field>`, multiple differing fields on the same row = multiple lines; `Diff` also contains source/target, but the current CLI does not print them), rather than whole-row summaries. The target must be an M7 DB **not yet in raft mode**, with version/admin/vault consistent with the export, no `[cluster]`, site changelog lag=0, and `site_apply_dead` empty; `--overwrite` is required to overwrite target-only replication rows. After successful cutover it writes `raft_cutover` and sets `raft_mode=on` (afterwards a startup without `[raft]` is rejected).
3. Start A (`bootstrap=true`), B (`false`), pair via the console, add C via `raft-add-witness`.

**force recovery** (A+B permanently lost, only export/backup remains):

1. Prepare a **clean target control DB**: same version, already `raft-cutover` to raft mode, `raft_applied` empty, no `raft_snapshot` rows, local admin present (**witness target exception**: a witness can recover without a local admin; the install owner writes sentinel `0`); the `raft.db` path must be brand new/empty.
2. `oss-server raft-force-recover --config survivor/oss.toml --from export.json --node-id N --yes` — imports the 11 tables and `initialize({N})` on an empty log; does not reset/overwrite existing `raft_applied`, refuses if non-empty. `--config` may also point to the witness's `witness.toml` (`[raft].state_db` opened via `Db::connect_witness`; data-site config preferred), and after recovery it likewise starts with `bootstrap=false`.
3. Start that node with `bootstrap=false` (the identity check compares `raft_bootstrap=0`, no re-initialize); other sites join via the pairing/learner flow after recovery.
4. Restore objects from backup/offsite replicas; run `sync-reconcile --repair` after the sync bucket peer recovers; both stretch sites' data must be restored from backups. Uncommitted writes are lost.
5. Single permanent loss: **C lost** → A+B still quorum 2; deploy a new witness (new node_id = current max + 1), add as learner, catch up, then replace; **B permanently lost and sync buckets exist** → A+C still quorum 2, deploy B′ reusing the old B's site UUID/token and a new Raft node_id; until `sync-reconcile --repair` completes it must not be marked serviceable (`DELETE /sites` should 409 when sync buckets exist); **A+B lost simultaneously** → force recovery as above.
6. **Upgrade order (M9 control-plane Level B rolling + Level C foundations; the data plane uses mixed-version gating)**: Raft RPC carries and validates `x-oss-raft-target-node-id` (prevents a new node_id on an old endpoint from mistakenly answering old membership requests), v1.13.1 is the rolling baseline; this version adds the `x-oss-raft-wire-version` / `x-oss-raft-feature-level` handshake (missing/invalid = 1). Steps:
   - **Binary rolling (feature level 1)**: restart one machine at a time, **followers/learners first, leader last**; after each restart wait for `applied` to catch up in `/api/v1/site/raft/status` before touching the next one. At this stage keep `[raft].feature_level=1` (default, old configs need no change), behavior identical to older versions.
   - **Enable level 2**: after all voters/learners are on the new binary (`wire_version=2`), write `[raft].feature_level=2` into the config one machine at a time and restart. The leader's `effective_feature_level` is only 2 when all current voters **and learners** have declared 2 in the current term; otherwise level-2 writes return 503 `{"error":"feature_unavailable","required":N,"effective":M}`.
   - **Activation = point of no return**: when the first level-2 entry commits, the same apply transaction writes `schema_meta.raft_feature_level=2` (only increases, never decreases). Afterwards rollback must switch back to a binary that supports that level; if the marker is higher than the config or binary limit, startup is refused outright. **Rollback is only possible before activation**: stop the cluster, switch back to the old binary, delete the `feature_level` key (the old `RaftToml` rejects unknown keys), start.
   - **Level-2 command**: the only product-level level-2 command is `BucketSetLifecycleV2` (structured lifecycle rules with filter/multiple transitions/Date/Noncurrent). At `feature_level=1` such writes are rejected before append with 503 `{"error":"feature_unavailable","required":2,"effective":1}`; rules expressible in the old columns still use V1 and behave unchanged. The first structured rule activates `schema_meta.raft_feature_level=2` (point of no return as above).
   - **No membership changes within the window**: the new leader pre-checks before add/promote/replace — any existing voter/learner with `wire<2`, target below standard, or unreachable → 409 `peer_incompatible`; an unreachable old node can only be removed/replaced. Console pairing (`/sites`, `/join`) likewise requires the peer identity to carry wire 2 and feature not lower than this node (old nodes default = 1 → 409).
   - **Level 3 / OSSCTL3 (v1.19.0 foundations)**: `MAX_FEATURE_LEVEL=3`. After all voters/learners run an OSSCTL3-capable binary, write `[raft].feature_level=3` into the config one machine at a time and restart; level-3 data (accounts/members, the `m8.runstate` extension, `ControlCommand::Ext`) is rejected before append/install while effective<3. The production Ext registry is empty — level 3 only means "can decode the Ext container", and **no product-level Ext command exists**. The first level-3 data/command write activates marker=3; an OSSCTL3 environment cannot roll back to v1.18 or earlier.
   - **OSSCTL1/2/3 snapshots and cutover**: the encoder selects the format by data/activation level; `lifecycle_rules.config_json` or an activated level 2 writes OSSCTL2 (magic + SHA-256 + feature_level + data); account rows, non-empty `extensions` (e.g. `m8.runstate`) or an activated level 3 writes OSSCTL3 (OSSCTL2 + opaque extension area). New/old binaries read older formats; old readers reject newer formats cleanly (no silent row loss). `raft-cutover` (including dry-run), `raft-force-recover` and store snapshot install monotonically raise `schema_meta.raft_feature_level` according to the data requirements in the same transaction. Rule: upgrade all voters/learners to a binary supporting the target level before activating it; OSSCTL2/3 environments cannot roll back to versions that only read older formats.
   - **LC-0 provenance**: exports record snapshot_format/wire_version/feature_level/source_build; cutover/force-recover validate them before any write (missing provenance on old exports is accepted with a warning; explicit fields are strict).
   - **Outside this release**: real-binary rolling e2e for the M3/M4 data plane, TLS material hot rotation, cross-major upgrade from < v1.13.1; shrink `apply`/`verify`/`commit`/`rollback`, Raft tenancy account commands/APIs and the canonicalization worker, the M8 multi-node runtime (Tasks 5–13), and production Level C Ext commands. DP-1 provides mixed-version gating and degradation headers (see M3 boundaries); LC-0 keeps export/cutover/force-recover provenance checks (missing provenance on old exports is accepted with a warning; explicit fields are strict), but full Level C bidirectional mixed writes still need the follow-up patch line.
   - Full drill: `tests/e2e_m9_rolling.sh` (requires `OSS_OLD_BIN` = v1.13.1; SKIP if not provided).

### Deployment and Security Boundaries

- Raft/site/mesh transport is plaintext by default; production deployments should configure `[tls.server]` (see the TLS section) to enable full-chain TLS/mTLS. When not enabled, deploy only on a controlled private network or behind external TLS termination/tunnels; `cluster_token`, `site.token`, `mesh_secret` must not appear on the public internet.
- Capability switches are flipped (`RAFT_READY`/`SYNC_READY`/`STRETCH_READY=true`). The control plane supports 1–3 voters: 2 voters after A/B pairing, 3 voters after `raft-add-witness` adds C (quorum 2, `production_ready=true`); single-node bootstrap is still usable for development. `tests/e2e_m9.sh` (3 processes) and `tests/e2e_stretch.sh` have passed locally; before going live you should still re-run on the target network and keep evidence.
